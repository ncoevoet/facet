# Sticky, tested-working dependency lock for the DEFAULT Docker images: the CUDA
# one (pytorch/pytorch:2.11.0-cuda12.8-cudnn9-runtime, torch 2.11.0+cu128, cubins
# sm_75...sm_120) and the slim CPU one, which share this file. The legacy CUDA
# image (torch 2.6.0 / CUDA 12.6, sm_50...sm_90) installs
# requirements.legacy.lock.txt instead; the Dockerfile picks with
# REQUIREMENTS_LOCK, set per variant in docker-publish.yml. See issue #119.
# Container-validated at transformers 5.15.0 on 2026-08-13 against the torch
# 2.6.0 base: a 16gb-profile GPU container built from this lock scanned 63 photos
# with 0 errors and build-tools/verify_scan_db.py passed (embeddings, VLM tags,
# aesthetic, saliency, faces, moments all populated and in range). Re-validated
# 2026-09-01 against the 2.11.0-cuda12.8 base: every pin below installs at
# exactly this version and pip's plan touches no torch/torchvision/nvidia-*/triton
# wheel. That container had no GPU, so the scan run above still dates from 2.6.0.
# Pin discipline learned the hard way: a sympy that does not satisfy the BASE
# IMAGE's torch makes pip resolve the conflict by replacing that torch with a
# PyPI build — the sympy==1.13.1 this file used to carry plans torch 2.6.0 plus
# the CUDA 12.4 nvidia-* wheels over the 2.11.0 base, silently undoing the point
# of using a CUDA base image at all.
# The cuML layer installed AFTER this lock intentionally downgrades
# numba/llvmlite/pandas/pyarrow — the container's final versions for those four
# differ from these pins by design; do not "fix" them from a container freeze.
# torch/torchvision + nvidia-*/triton are intentionally omitted — the CUDA base
# image already provides them, and the CPU image installs torch from the CPU
# wheel index before this lock (see the Dockerfile).
