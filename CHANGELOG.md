# Changelog

All notable changes to Facet are documented in this file.

## [Unreleased]

### Changed

- **`scoring_config.json` is now your override, not the whole configuration** ([#118](https://github.com/ncoevoet/facet/issues/118)). Every value Facet ships lives in `config/scoring_config.default.json`, and your file is resolved on top of it — so it needs to hold only the settings you actually changed, and anything you leave out keeps the shipped value and picks up improvements to it when you upgrade. The shipped configuration itself reduces to nothing: the file this repository tracked, all 3780 lines of it, is now an empty override. Objects merge key by key; arrays REPLACE wholesale, which is not a simplification but the only semantics this config can carry — `categories` is first-match-wins over a priority sort that breaks ties on array position, `scoring_contexts.*.promote` is read in the order given, and an element-wise merge would both reorder scoring silently and resurrect a category you had deliberately deleted. The practical consequence is that changing one category weight means your file carries the whole `categories` array; everything else still stays out of it. **Upgrading:** nothing to do — a full config from an earlier release resolves to itself and keeps working. Run `python database.py --compact-config` when you want it reduced to just your own edits; it takes a `0600` backup first and is lossless, the file resolving to exactly the same configuration afterwards. The trade-off, stated plainly: a value dropped because it matched the default will follow that default if a later release changes it, which is how new tuning reaches you without editing your file — pin it explicitly if you would rather it did not.
- **A fresh Docker install no longer starts on values nobody chose.** The image seeded `/config/scoring_config.json` from a `scoring_config.default.json` that was maintained by hand alongside the config this project actually edits, and the two had drifted: the defaults were missing fourteen key paths, among them the whole `auto_cull`, `auto_retrain`, `critique`, `immich`, `skin_tone` and `distortion_attributes` blocks, three `viewer.features` flags, the three darktable preview keys and the two `face_detection` expression thresholds. Every consumer falls back to a hardcoded default of its own, so the failure was silent — a container simply scored and culled with values that were not the shipped ones, while `docs/CONFIGURATION.md` documented something else. The clearest case is the tagger: the commit that taught the vocabulary the word *dance* touched only the live config, so every Docker install since has had a `sports` category that could not match a dance photo, which is exactly the failure that commit set out to fix. The defaults are now generated from the live config rather than kept in step by vigilance, and the container seeds an empty override instead of a copy, so there is nothing left to drift.
- **The SQLite pragmas, the retrain window and the RAW backend are read from the defaults too.** `db/connection.py`, `optimization/auto_retrain.py`, `optimization/personal_ranker.py`, `diagnostics.py`, `viewer.py` and `facet.py` each read one corner of the config directly, with a hardcoded fallback. Against an override file every one of those fallbacks would have fired — the pragmas alone would have dropped from the shipped 2048/128 MB to 256/64 — so they now resolve the config the same way everything else does. `db.connection` and `viewer` used to carry private copies of the path resolution because they cannot import the `config` package without recursing through `db`; they now share one stdlib-only module, since a copied resolver is how the defaults drifted in the first place.

- **Which `scoring_config.json` a bare command reads is now stated, and no longer depends on where you stand.** With neither `--config` nor `$FACET_CONFIG` set, a config in the working directory still wins — a photo library can carry its own — but when there is none, the file beside the install is read instead of the working directory's absent one. Those were the same thing while an absent config raised, and stopped being the same thing when running on the shipped defaults became supported: `python /opt/facet/facet.py` from anywhere else quietly scored on defaults while your real config sat unread in the install root. [docs/COMMANDS.md](docs/COMMANDS.md#configuration) now works the resolution order through all four cases.

### Fixed

- **A config file Facet creates is owner-only (`0600`).** It ships as an absent override, so the first weights, priority or `--add-user` write is what creates it — and it holds `viewer.password`, `users.*.password_hash`, `upload.password`, `frame.tokens` and `immich.api_key` in plaintext. It was created at the umask default, typically `0664`, and every later write preserved those bits, so a group- and world-readable credentials file stayed that way permanently. A config that already exists keeps whatever mode you gave it.
- **`calibrate.py --apply` no longer discards a completed run on a fresh install.** It refused to write when `scoring_config.json` did not exist — the ordinary state now — after the optimisation had already finished.
- **`--doctor` stops reporting a healthy install as broken.** An absent override was flagged `[!!] Config: not found`, and the same guard silently dropped the configured VRAM profile and the config-schema check along with it, on exactly the install nobody has inspected yet.
- **A config that is valid JSON but not an object is rejected by name.** It previously died inside the merge with an `AttributeError`, which was then reported as being unable to *parse* a file that had parsed perfectly — sending you after a syntax error that was not there.
- **Two commands announced a backup that was never written.** `database.py --add-user` and `facet.py --apply-recommendations` printed a rollback path that held nothing, immediately before rewriting the config.
- **Timestamped config backups and crash-left staging copies stay out of the Docker build context.** `.dockerignore` matched only the literal `scoring_config.json.backup`, not the `.backup.<timestamp>` files every write leaves nor `.scoring_config.tmp*` — each a complete config, with credentials, uploaded to the daemon and cached by BuildKit.
- **Opening a database no longer re-resolves the whole configuration.** Reading two SQLite pragmas parsed the ~97 KB defaults and deep-copied the result on every connection, so at least once per API request: measured 1.63 ms, now 0.0022 ms. Edits to the `performance` block still take effect on the next connection, with no restart.

### Added

- **`python database.py --compact-config`** rewrites `scoring_config.json` as the override it is, dropping every value equal to the shipped default. Lossless by construction, and it takes an owner-only backup first because the file legitimately holds `viewer.password`, `users.*.password_hash`, `upload.password`, `frame.tokens` and `immich.api_key` in plaintext.

## [1.14.2] "Halide" — 2026-09-01

### Added

- **A third CUDA image, `ghcr.io/ncoevoet/facet:latest-cuda-legacy`, is published for GPUs the default CUDA image no longer supports.** Fixing Blackwell (see Fixed, below) meant bumping `latest-cuda`'s base to `pytorch/pytorch:2.11.0-cuda12.8-cudnn9-runtime`, whose torch build ships `sm_75`-`sm_120` cubins — Turing through Blackwell — and drops `sm_50`/`sm_60`/`sm_70`, the architectures Maxwell, Pascal (GTX 900/10-series) and Volta cards use. `latest-cuda-legacy` keeps today's base, `pytorch/pytorch:2.6.0-cuda12.6-cudnn9-runtime` (`sm_50`-`sm_90`), so those cards keep working — an owner on one of them switches the `image:` line in their compose file, or the tag on a bare `docker pull`. The four GPU compose files (`docker-compose.{8gb,16gb,24gb,gpu}.yml`) still pull `latest-cuda` unchanged, so current-generation hardware needs no action. A second lock file, `requirements.legacy.lock.txt`, keeps the two CUDA bases from fighting over one pinned dependency graph — see Fixed, below.
- **`--doctor`, and Facet's own device selection, now catch a GPU the driver sees but this PyTorch build ships no kernels for.** `torch.cuda.is_available()` only checks for a driver and a device; it never checked whether the installed build actually has kernels for that device's architecture, which is exactly how the Blackwell crash below went undetected until the first real tensor op. Facet now compares the device's compute capability against `torch.cuda.get_arch_list()` and launches one throwaway kernel before committing a VRAM profile; a mismatch falls back to CPU instead of dying on the first inference call, and points the run at `--doctor` for the reason. `--doctor` is where the fix is actually spelled out: the mismatched compute capability, the build's architecture list, and the image tag (Docker) or `--index-url` (bare metal) to switch to. The check fails open: a torch build exposing neither `get_arch_list` nor a usable allocator is reported usable rather than vetoed, since disabling a GPU that actually works would be the worse failure. Every surface that asks "is there a GPU" now asks this one question rather than `torch.cuda.is_available()` — VRAM sizing (`ModelManager.detect_vram`, which decides pass grouping and whether the RAM-safe chunk start applies), OCR's easyocr engine, and the `/metrics` and resource-monitor GPU gauges — so a machine cannot be simultaneously reported as running on CPU and budgeted as a 16 GB GPU.

### Fixed

- **RTX 50-series (Blackwell) GPUs crashed on the first CUDA operation on the published `latest-cuda` image, instead of running.** The image was pinned to `pytorch/pytorch:2.6.0-cuda12.6-cudnn9-runtime`, whose torch build ships kernels for `sm_50` through `sm_90` — Blackwell is `sm_120`. `torch.cuda.is_available()` still reported `True` on these cards, so the crash landed on the first tensor operation rather than at startup: "no kernel image is available for execution on the device". `latest-cuda` now builds from `pytorch/pytorch:2.11.0-cuda12.8-cudnn9-runtime` (`sm_75`-`sm_120`); cards the new base no longer covers get their own image, `latest-cuda-legacy` (see Added, above). (issue #119)
- **The published "CPU" image, `ghcr.io/ncoevoet/facet:latest`, actually shipped a full CUDA build of PyTorch.** `requirements.lock.txt` pinned `sympy==1.13.1`, which only torch 2.6.0 requires exactly; installing that lock over the image's CPU-wheel torch left pip unable to satisfy both, and it resolved the conflict by discarding the CPU-only torch for a CUDA build pulled unpinned from PyPI's default index. Measured on the published image: `torch 2.6.0+cu124`, CUDA reported as `12.4`, 13 `nvidia-*` wheels installed, 8.81 GB on disk — none of which a slim CPU build should carry. Rebuilt from this branch with `sympy` bumped to `1.14.0` — the version the 2.11.0-cuda12.8 base ships, which satisfies torch 2.11.0's `sympy>=1.13.3` requirement: `torch 2.13.0+cpu`, no CUDA, zero `nvidia-*` wheels, 3.34 GB.
- **`install.sh` routed a driver reporting CUDA 12.6 or 12.7 to the `cu124` PyTorch wheel index, up to three point-releases behind.** The version ladder had no branch between `>= 12.8` and `>= 12.4`, so 12.6/12.7 fell through to the `cu124` case. A `cu126` branch now sits between them.
- **`install.sh` picked the PyTorch wheel from the driver's CUDA version alone, stranding pre-Turing cards on a build with no kernels for them.** A GTX 10-series (`sm_61`) or Titan V (`sm_70`) box behind a modern driver has `nvidia-smi` report "CUDA Version: 12.8" exactly as an RTX 5090 does, so it installed the `cu128` wheel — whose compiled architectures start at `sm_75` (verified from the wheel: `sm_70 sm_75 sm_80 sm_86 sm_90 sm_100 sm_120` on 2.10.0+cu128, and `sm_75` upward on the 2.11 line). That card then died with the same "no kernel image is available for execution on the device" this release exists to eliminate, from the opposite direction. `install.sh` now also reads the lowest installed card's compute capability and floors the choice at `cu126` (`sm_50`-`sm_90`) below `sm_75`, which is the bare-metal twin of the `latest-cuda` / `latest-cuda-legacy` image split. A card whose capability `nvidia-smi` is too old to report keeps the previous driver-only behaviour.

### Security

- **Five undici advisories, one high, are closed in the client's build-time dependency tree.** `undici` reached the tree transitively through `@angular/build` and `jsdom`, at a version inside the vulnerable `>= 7.0.0 < 7.29.0` range: CVE-2026-13697 (cross-user disclosure and a parse-time crash via degenerate private cache directives, high), plus CRLF injection via a blob-like body `type`, cross-user disclosure via whitespace around equals in `Cache-Control`, cookie attribute injection via unsanitized domain fields, and downstream response desynchronization in the retry interceptor. Pinned to 7.29.0 with an `overrides` entry rather than by moving the framework: `npm audit fix --force` wanted `@angular/build` 21.2.22, outside the exact 21.2.19 this project pins. Build-time only — no shipped runtime code imports it.

## [1.14.1] "Isochrone" — 2026-08-23

### Added

- **The timeline says when filters are hiding photos, and offers to show them.** Making the timeline honour the gallery's hide toggles (below) means a day whose every frame is a burst follower or a blink now counts zero, and a zero-count day cell is deliberately not clickable — so without a way back those photos would be reachable from the gallery but not from the timeline at all. On the library this was measured against, three days went that way. The timeline toolbar, and its mobile bottom bar, now show a `visibility_off` button whenever any toggle is hiding something, captioned "Some photos are hidden by your filters", which clears the toggles the same way the gallery's own hidden-photos banner does. The stash-and-restore logic behind that banner moved from the gallery component into the shared store rather than being written a second time.

### Changed

- **Unloading a pass group's models collects once instead of once per model.** A full `gc.collect()` costs about 88 ms once torch, transformers and cv2 are loaded, and `unload_model` paid it for every model — nine times per chunk on the `8gb` CPU roster, on top of the one already at the chunk end, or roughly 0.79 s per chunk and 79 ms per photo at the container chunk size of ten. The models of a pass group are unloaded back to back with nothing allocated between them, so one collection reclaims exactly what nine do. Each model's reference is still dropped individually, so refcounting frees the non-cyclic bulk at the same instant either way; only the cycle collection, the device cache and the heap trim wait for the end of the group. Deferring cannot raise the peak, because the whole group was already resident during inference.

### Fixed

- **The published Docker images were built from an unlocked dependency tree.** `client/package-lock.json` was gitignored because `package.json` pins every version exactly — true of all 32 direct dependencies, and silent about the transitive graph beneath them, which `npm install` re-resolved from the registry on every build. The 1.14.1 image build failed on both targets with `npm error Cannot read properties of null (reading 'edgesOut')` against a `package.json` that differed from 1.14.0 by its version line alone: `node:22-alpine` had been republished with npm 10.9.8, which cannot resolve the current graph, and the tag is a moving target. The lock is now tracked and `npm ci` installs from it, skipping resolution entirely; the base image is pinned to an exact patch; and CI installs the same way, keyed on the lock, so it exercises the tree the image will get. The lock is generated under Alpine, because one made on glibc omits the musl-only optional packages `npm ci` requires.
- **The timeline, the folder browser and the gallery's type chips counted photos the gallery would not show.** All of them accepted `hide_blinks`/`hide_bursts`/`hide_duplicates` but defaulted them to off, and the viewer never sent them — so they answered over every frame in the library while the gallery they hand the user to answers over burst leads only. Against a 126k-photo library the per-day count the timeline advertised disagreed with what clicking that day actually opened on **73% of days** (one day offered 459 photos and opened 88), and the library as a whole was over-reported by 33% — 126,363 against the 84,634 the gallery shows. The same gap picked each day's hero thumbnail from frames the gallery hides, and left a shared album showing every frame of a burst to its recipient while its owner saw one. The five toggles are now resolved from `viewer.defaults` when a request omits them, through one helper the smart-album cover picker already needed and had grown its own copy of; `get_photo_types` learned the two set-collapsing toggles it never had, so the chips agree with the grid on brackets and panoramas too. Absent now means *use the configured default*, so a caller that genuinely wants everything must say `hide_bursts=0` — which is why the gallery's own endpoint keeps defaulting to off: its client omits the parameter entirely when the toggle is cleared, and defaulting it on would have made "Show all hidden" impossible to express. Manual albums are deliberately untouched: an album is an explicit list, and hiding rows a user put there by hand would discard the choice they made.
- **Memory sizing honours the container's memory limit instead of the host's RAM.** `psutil.virtual_memory()` reads `/proc/meminfo`, which Docker does not virtualise, so every memory decision Facet made inside a container was sized against the host. The failure was not that the brake failed to engage — the throttle opened: on a 23 GiB host capped at `mem_limit: 8g`, the multi-pass monitor saw ~26 % used, read that as headroom, and grew `ram_chunk_size` by 25 % every three samples, while the 85 % reduce path stayed unreachable because the host would have had to reach 19.5 GiB used first. Reproduced on a published image predating the fix (v1.7.2) at `--memory=8g`: `OOMKilled`, exit 137, dead at 0/200 photos, having reported `Mode: CPU-only (47GB RAM)` from inside the 8 GiB container and planned every model into one `~15.0GB` pass. A new `utils/system_memory.py` reads the container's limit (cgroup v2 `memory.max`, v1 `memory.limit_in_bytes`) and charges usage to the cgroup's own accounting — v2 `anon`, v1 `total_rss`/`rss` — rather than host free memory, falling back to psutil unchanged when no limit applies. Reading v1's `memory.usage_in_bytes` instead would have been worse than the bug: it counts page cache, so on the live 16 GiB container measured here it reports 89 % where `anon` reports 50 %, welding every brake on for Synology DSM and every other v1 host. All eight host-RAM readers now route through it: both resource monitors, the face brake, `_can_cache_to_ram`, `detect_system_ram_gb`, the RAW-decode governor and the profile diagnostic. The CPU pass planner is bounded on both paths, because sizing a pass against total memory claims memory that is not the process's to claim: under a limit a pass may plan `min(limit - 2 GB, 5 GB)`, and on bare metal `(total - 1 GB) / 1.6`, where 1.6 is the measured ratio of real RSS to declared model weight — a 5.0 GB pass survived an 8 GiB budget and a 6.0 GB one was OOM-killed twice. That removes a 6.0 GB pass an 8 GB host used to plan, leaves hosts of 33 GB and up untouched, and where no pass can fit at all the planner now says so by name instead of leaving the kernel to explain it. Two limits remain: a model larger than the budget cannot be split, and `MODEL_RAM_REQUIREMENTS` prices weight only, so real peak — 12.55 GB of anonymous memory for the `8gb` profile on CPU — runs well above it.
- **The container's memory limit is found where it actually sits, not only at the cgroup root.** The limit was read from the fixed paths `/sys/fs/cgroup/memory.max` and `memory/memory.limit_in_bytes`, which name the namespace *root*. That is right for default Docker, Podman and Kubernetes, where the container's own cgroup is mounted there, and those keep reading exactly the same two files. It is wrong wherever the limit sits on a cgroup this process does not own the root of: `docker run --cgroupns=host`, or a systemd unit carrying `MemoryMax=` — which the `facet.service` unit in [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md) invites. There the root reads `max`, the limit was taken as unlimited, and every consumer silently fell back to host RAM: the original issue #111 failure again, minus the log line that would have revealed it. `/proc/self/cgroup` now names the cgroup, and the limit is the tightest found walking it to the root, because a slice can cap a parent while the leaf still reads `max` and it is the smallest that binds. Usage is charged to the cgroup the limit came from, since a slice-wide cap is charged for every unit beneath it — reading one unit's own `anon` against its parent's limit overstates the headroom, and overstating is the direction that ends in a kill. Two helpers move into `utils/system_memory.py` so their consumers stop reimplementing them: `BYTES_PER_GB`, declared by hand in two modules, and `total_gb()`, derived in two more with a bare `1024 ** 3` and two different unknown-sentinels.
- **The chunk auto-tuner grew on the trough between passes rather than on what the chunk actually cost.** Reading the cgroup instead of the host fixed the denominator, not the policy, and a 50-photo scan in an 8 GiB container was still OOM-killed at the start of its second chunk on both the `legacy` and `8gb` profiles. A chunk is not one memory reading: it decodes its images, then runs each pass in turn, and every unload between passes drops usage almost to the floor, so a monitor sampling every five seconds is as likely to catch the trough as the peak. Three troughs in a row cleared the "well below the limit" bar and grew the chunk 25 %. Replaying the anonymous-memory trace measured inside the container through the monitor's own decision body, `ram_chunk_size` ran 10 → 12 → 15 → … → 500 during the *first* chunk and was clamped back to 375 — so the second chunk tried to decode every remaining photo at once and died before it loaded a single model. Growth is now decided once per chunk, at the boundary where the previous chunk's images have been released and none have been decoded for the next, and only when that whole chunk's high-water mark stayed below the threshold; the reduce path stays instantaneous, because it is the brake. Every adjustment is now logged as it happens. Previously they were recorded only for the end-of-run summary, which never prints when the kernel kills the process — so the tuning that caused the kill left no trace in the log at all, and its absence there was easy to mistake for evidence that no tuning had occurred.
- **Unloading a model returned nothing to the kernel.** Freeing a model is not the same as giving its memory back: glibc raises its `mmap` threshold each time a large mapped block is freed, so after the first model the thousands of medium tensors making up the next one come from the heap arenas instead, and an arena is only ever released from its top. Measured in an 8 GiB container on the `legacy` profile, the process sat at 5.62 GiB of anonymous memory from the first pass onward and did not move when `topiq_iaa` was unloaded — 0.11 GiB, against weights ten times that — nor when the next model was loaded in its place. Every later pass therefore ran on top of a high-water mark it could not use, while the pass planner budgeted as though the memory had been returned. `utils/system_memory.release_freed_heap()` calls `malloc_trim`, which walks the arenas and hands their free pages back, and is now called after each unload, after `unload_all`, after a cache eviction and at each chunk boundary. The same 0.74 GiB of touched tensors measures 1.214 GiB of RSS after `del` and `gc.collect()` and 0.479 GiB after this call. It resolves the symbol through the process's own namespace rather than naming a soname, so on musl and macOS, where it does not exist, the behaviour is unchanged rather than broken. This was necessary but not sufficient on its own: an image carrying only this fix was still OOM-killed by the tuner above.
- **The Docker config survives `down && up`.** `scoring_config.json` was baked into the image, so the viewer-password upgrade, the share-secret eviction and every weights, priorities or scoring-context save made through the UI were discarded on container recreate; the compose bind mount that would have kept them was commented out. Uncommenting it was not the fix — for anyone running the published image without a git clone, the daemon creates an absent single-file mount source as a *directory*, which shadows the baked config and breaks a zero-config `docker compose up`, and the entrypoint cannot `rmdir` its own mount point. Compose now mounts a directory (`./facet-config:/config`) that the daemon can safely create, `docker-entrypoint.sh` seeds it from the image default on first run only and chowns the seeded file as well as its directory — the file explicitly, because the config's non-atomic writers need write access to it and not merely to the directory around it. A new `FACET_CONFIG` environment variable selects the path and is honoured by the viewer and by every `facet.py` entry point, so `docker compose exec facet python facet.py …` reads the same file the viewer writes; unset, it resolves to exactly the previous path. The container path is `/config` rather than `/app/config` because the latter is where the `config` Python package is baked, and mounting over it would shadow the package itself. **Upgrading:** if you customized `scoring_config.json` and uncommented the old `- ./scoring_config.json:/app/scoring_config.json` mount, run `mkdir -p facet-config && cp scoring_config.json facet-config/scoring_config.json` before adopting the new compose file — otherwise the entrypoint seeds a fresh default and your weights, categories and viewer password stop being read (and an empty `viewer.edition_password` disables edition gating entirely). Keeping your own compose with the old mount in place is also safe: the entrypoint seeds `./facet-config` from whatever `/app/scoring_config.json` holds, which is then your file, not the sanitized default. The seeded file is created `0600` rather than `0644`, because it legitimately holds `viewer.password`, `users.*.password_hash`, `upload.password`, `frame.tokens` and `immich.api_key` in plaintext, and the config writer preserves the destination mode on every later write; `facet-config/` is gitignored for the same reason.
- **Unloading a model freed nothing while the pass that ran it was still on the stack.** `malloc_trim` was called at the right moments, but `_process_chunk` still held each model in two places — its `loaded_models` entry and the load loop's own `model` local, which outlives its loop and pinned the last model of every pass group. The refcount never reached zero, so the trim walked arenas the weights still occupied and the reclaim slipped a whole pass; for the last pass of a chunk it slipped past the chunk-end trim entirely, which is the reading the tuner consults to decide whether the next chunk may grow. Under a container limit the RAM cache retains nothing and every model takes that path, so the regime the cgroup work exists to serve was the one where the trim freed least.
- **The face model is kept between chunks where the budget allows it.** Making it an ordinary managed model left it out of the RAM-cacheable set, and `FaceAnalyzer` exposes no `unload` or `cpu`, so every chunk reparsed 196 MB of ONNX weights and rebuilt three `InferenceSession`s — a thousand rebuilds on a 10 000-photo scan, where the container path pins the chunk to ten. It is now retained off CUDA, where moving it is a no-op and the object is simply held. The existing budget still refuses it under a tight limit, so an 8 GiB container keeps unloading it and the 2.0 GB reclaim is untouched; on CUDA its sessions pin VRAM, so it is never cached there. Measured over three chunks: one build instead of three on a 32 GiB host, still three at `--memory=8g`, still three on CUDA.
- **A cache eviction under memory pressure no longer stops halfway.** The restore side was fixed to a single `pop` because eviction deletes from the same dict on the monitor thread, but the eviction side still snapshotted the keys and deleted each one. A restore landing between the two raised `KeyError`, which the monitor swallows, leaving every model after the missing one cached — above 85 % of the effective limit, the moment the memory is most needed. `unload_all` had the same shape and runs while the monitor may still be inside an eviction, since `stop()` sets an event without joining.
- **A container large enough to hold a pass is no longer told to raise its memory limit.** Pass capacity is held at the packing ceiling, so it reads 5.0 GB at every limit above 7 GiB, and the 8.0 GB `qwen3_5_4b_tagger` exceeded it at every container size: a 64 GiB container was warned to expect an OOM kill and to raise a limit that raising could never clear. The kill is now predicted from what the container can actually hold, and a pass merely above the packing ceiling says so at info level, because that is a deliberate cap rather than a danger.
- **Subject saliency ran in fp16 on CPU, and its batch size ignored the memory budget entirely.** The published BiRefNet checkpoint is stored as F16 with no `torch_dtype` in its config, so `transformers` loaded it half-precision; CPU has no fp16 kernel path and falls back to an unvectorised one — a 256x256 forward measured 49.97s in fp16 against 1.10s in float32, and a single 1024x1024 forward ran for 28 minutes, so every scan on this branch crawled through this pass. Separately, `get_saliency_masks` batched a fixed 8 images at 1024x1024 regardless of what the process actually had: measured inside a container against the cgroup's own anon accounting, activations cost 2.32 GiB per image plus a 0.28 GiB intercept, while the pass planner prices the model's weight at 2.0 GB when it is really 0.36 GiB — so a fixed batch of 8 asked for roughly 18 GB whatever the container allowed, and the same container and photos were OOM-killed at exit 137 with `batch_size=8` while the derived batch survives at peak anon 4.85 GiB. The model now runs in float32 anywhere without a dedicated GPU, and the batch is derived from `effective_memory()`, with an explicit argument acting as a ceiling rather than a floor: it picks 1-2 images in 8 GiB, 4 in 16 GiB, and the previous 8 when memory is unlimited. CUDA is exempt, since its activations land in VRAM, which no cgroup limit governs.
- **The face model's memory stayed uncounted for the whole scan.** `Facet` built `FaceAnalyzer` in its constructor, which loads InsightFace immediately, and the multi-pass processor took that instance rather than loading one through the model manager, skipping it when unloading — so its declared 2.0 GB stayed resident from construction to the end of the scan while `group_passes_by_vram` budgeted it as a pass of its own. Every other pass was therefore understated by 2.0 GB: the 8 GiB container that appeared to sit exactly on its 5.0 GB budget was really at 7.0, or 11.2 GB of real RAM at the measured ratio, inside 8 GiB. InsightFace is now an ordinary managed model — `load_model_only` builds it and `unload_model` releases it, with no special case in the multi-pass processor — dropping residency from 15 of 15 passes to 3 of 15, one per chunk, and the 8 GiB peak to the 5.0 GB actually planned.
- **The CPU model cache retained models the running pass had no room for.** `unload_model` decided at unload time whether to keep a model in `_cpu_cache`, bounded only by a free-memory threshold, and never re-validated that against the next pass's own budget once it loaded on top. On CPU that retention is not a cheap handle: `_move_to_cpu` is a no-op there — measured at 0.0005 GB freed, with the parameter storage pointer unchanged — so a retained model keeps its whole footprint, and real co-residency is the running pass plus everything still cached. The bound failed in exactly the wrong direction: the roomier the budget, the more it retained. Replaying the `8gb` profile's five-pass plan through the real unload cycle, an 8 GiB container retained nothing and peaked at its planned 5.0 GB, while a 16 GiB one started retaining at pass 3 and kept growing — the 12.55 GB of anonymous memory measured on a live 16 GiB container against the same 5.0 GB plan. `_can_cache_to_ram` now also computes the exact peak the retained set would reach beside the heaviest planned pass, excluding models that pass would load anyway, and refuses to cache past it.

### Security

- **A mistyped `$FACET_CONFIG` no longer reads as a never-configured install.** Before the config path became environment-driven it was derived from `__file__` and could not be misaimed, so "file absent" genuinely meant "fresh install" and the open-install auth path was sound. The variable is taken verbatim, with no existence check and no distinction between unset and set-to-a-missing-path, so a one-character typo in the mount or the compose file flipped a password-protected install to fully open: an anonymous caller reported both authenticated and edition rights. The only thing keeping that off the wire was an unrelated component raising `FileNotFoundError` on the same path during startup — fail-closed by accident rather than by decision. A path the operator NAMED is now distinguished from the default: when it does not exist the install refuses the open-install path and says so at ERROR, where it is visible under the container's default `INFO` level, instead of the `DEBUG` line nobody saw. An unset variable with no config present still behaves exactly as before, so a zero-config first run is unaffected.
- **Applying optimized weights no longer widens the config's permissions.** `docker-entrypoint.sh` seeds `scoring_config.json` at `0600` because it holds `viewer.password`, `users.*.password_hash`, `upload.password`, `frame.tokens` and `immich.api_key` in plaintext, and compose promises the mode survives every later write. That held for the shared config writer but not for `--optimize-weights --apply`, which used a local `open()` + `os.replace()`: the destination inherited the temp file's umask mode, and every later write then faithfully preserved the widened one, leaving the install's plaintext password readable by every account on the host. Its scratch file was also named `scoring_config.json.tmp`, which no ignore rule covers, so a crash between write and rename left a complete copy of that config under a stageable name. Both are settled by writing through the shared writer, which copies the destination's mode and stages under the ignored dotted prefix. The read-modify-write now also runs under the config write lock every other writer shares.
- **`docker compose build` no longer sends live config secrets into the build context.** `facet-config/` and `.env` were added to `.gitignore` for the secrets they hold but never to `.dockerignore`, and compose builds from `.` with `./facet-config` mounted inside that context — so a build on a live install shipped the viewer password, every password hash, the Immich API key and the `.facet_secret` JWT signing key to the daemon and into BuildKit's context cache. No `COPY` named any of them, so nothing was baked into a layer, but the transfer alone crosses a real boundary for a remote `DOCKER_HOST`, a cloud builder or CI. The root-level `scoring_config.json` of a native install was exposed the same way and is excluded too; only `scoring_config.default.json` is ever a `COPY` source.
- **`docker-entrypoint.sh` no longer trusts a symlink where it is about to write as root.** The config seed and the ownership fix-up both run, as root, over `/config` — a directory already chowned to the unprivileged `facet` user — so anyone with code execution as `facet` could plant `scoring_config.json` as a symlink to a root-owned path and have the root-run `cp`/`chown` write or retarget through it; the previous `[ ! -f ]` guard does not even see a dangling symlink. Both now refuse a symlinked seed target, and the ownership fix-up runs `chown -h` so a planted symlink among the directories it touches is retargeted rather than followed. The seeded file is created `0600` rather than the `cp` default of `0644` — the same plaintext-credentials rationale as above — and an unwritable `/config` now falls back to the image's own config instead of leaving `FACET_CONFIG` pointed at a file that was never created. The unprivileged `user:` compose override, which skips the root branch entirely, now seeds its own config too rather than failing to start.

## [1.13.0] "Sténopé" — 2026-08-17

### Fixed

- **RAW frames of an exposure bracket no longer render at the same brightness.** Every decode passed `no_auto_bright=False` to LibRaw, enabling a per-frame gain that scales an image until roughly 1% of *its own* pixels clip; the gain can only ever brighten, so applied independently it pulled the dark rungs of a bracket up toward the base exposure. A second per-frame term, `adjust_maximum_thr`, was never passed either, so its 0.75 default replaced the camera's white level with that frame's brightest pixel. On a real five-frame Canon EOS 6D bracket spanning 6.7 stops, the −3.42 EV, −1.74 EV and 0.00 EV frames rendered at means of 56.3, 55.2 and 54.1; the ladder now spans 17.57×. RAW only — JPEG and HEIF were never affected. ([#105](https://github.com/ncoevoet/facet/issues/105))
- **The CLIP-MLP aesthetic score on `legacy`/`8gb` was an untrained network.** The scorer built a 768-256-1 model for a 1024/128/64/16 checkpoint and `strict=False` swallowed all fourteen mismatched keys, so every parameter stayed at its random initialisation — the same 200 photos scored 4.870, 5.344 and 5.347 under three different seeds. The correct definition existed in `ModelManager` but sat in a path `_select_models` never appends. Rank correlation against an independent aesthetic model rises from 0.072 to 0.297; because the old ordering was noise, the new one is unrelated to it.
- **The `24gb` profile ran no composition model at all.** It was configured for `qwen2-vl-2b`, which the default multi-pass scan never dispatches, so those libraries silently received rule-based CPU composition and no `composition_pattern`. Rule-based and SAMP-Net scores are statistically uncorrelated on real data (Spearman 0.025), so this was a different signal rather than an offset. `24gb` now uses SAMP-Net like every other profile, and a configured composition model with no pass logs a warning instead of vanishing.
- **`--refresh-thumbnails` deadlocked on its own worker pool.** Tasks submitted nested decodes to the same bounded executor and waited on them, so it hung rather than failed — indistinguishable from a slow migration over a NAS.
- **Cull-to-folder refusals were undiagnosable.** The server's actionable message fired only when the allow-list was empty, which cannot happen once scan directories are always appended, and the client discarded the detail regardless. The 403 now names `viewer.export.allowed_target_dirs` and the roots it resolved, and the interceptor and both dialogs surface it.
- **The best-of-burst badge rendered for the first time.** It read `is_best_of_burst`, a field that has never existed in any API payload; it now reads `is_burst_lead` and requires actual burst membership.
- **`/image?fallback=thumbnail` returned 500 instead of degrading** when a RAW decode failed, because the new decode raised a `RuntimeError` the fallback did not catch.

### Added

- **Per-channel clipping detection, indicators, badge and filter.** Stored histograms carry luma plus R/G/B as 4×256 uint16, and true clipped fractions — exactly bin 0 and bin 255, per channel — are derived from that blob without decoding the image again. The gallery badge threshold was chosen from measurement: across 28 photos of a real library, a badge at 0.1% fires on 54% of them and at 5% on 4%. Shadow clipping is off by default because it is so often deliberate.
- **A full-resolution RGB histogram in the viewer**, switchable between luminance, RGB and each channel alone, normalised over the interior bins so a blown highlight can no longer flatten the tonal curve into a hairline. Monochrome photos show luminance only.
- **Set membership in photo details** — the bracket, panorama, burst or duplicate a frame belongs to, with its siblings, their EV offsets, and a way to scope the gallery to that one set.
- **`--refresh-thumbnails`** regenerates stored thumbnails from each file's embedded preview without a rescan, and **`--backfill-clipping`** derives the new per-channel percentages from histograms already stored. A banner reports how many rows are still pending.
- **`--check-raw-rendering`** renders sample photos under current and candidate settings so decode settings can be validated before committing a large scan to them.

### Changed

### Added
- **`--tag-untagged` tags only the photos that have none**, from stored embeddings and without reading a single image — the same work a scan already does at the end. The capability existed as `tag_existing.py`, but nobody looked there: every other maintenance operation is a `facet.py` flag, so this one was effectively invisible even to people who knew the project.
- **A `windows-latest` CI job** covering `tests/test_scan.py` and `tests/test_device.py`. CI ran on Linux only, so the library lock's Windows backend and the Apple Metal device policy had never been exercised by it — which is how the two lock bugs below survived. Deliberately not the whole suite: much of it hard-codes POSIX paths, and a permanently red job is an ignored one.

### Fixed
- **Re-clustering no longer orphans the people you named.** `--cluster-faces-incremental` promises to preserve existing persons, and preserved the *records*: every mode but `--cluster-faces-force` clears face→person assignments and rebuilds them, returning a cluster to a person only when its mean embedding is within `merge_threshold` of that person's single stored centroid. Someone photographed across years spans a broad region, so HDBSCAN correctly splits them into tight sub-clusters that each sit far from that average, fail the threshold, and become a new anonymous person. Measured on a 145,677-face library the pass returned **38%** of the faces attached to named people — the largest three kept 19%, 4% and 9%, while small, visually consistent people kept over 90%. The failure scaled with how much had been curated. The pass already snapshots who owned every face before it starts and already consults that snapshot for faces HDBSCAN calls noise; asking the same question of a cluster — if most of it belonged to one person before, it still does — returns **96%**, recovering 24,409 faces across 5,687 clusters. It defers to the previous assignment, so an earlier mis-assignment is carried forward rather than corrected: that is the contract of a mode whose purpose is preserving existing persons, and `--cluster-faces-force` still re-derives everything.
- **A tagging pass no longer dies on a library holding two embedding widths.** Switching `vram_profile` swaps the image tower (CLIP 768 ↔ SigLIP 1152) while rows written by the previous one stay as they were, and the tagger scored every row against the active tower with no dimension check — so one stale row raised a bare shape mismatch that took down the caller. On a 129k library with 836 such rows that killed the whole post-processing tail of every scan: tagging, moment detection, junk detection and vec population, all skipped after the scoring run had succeeded. 26,451 photos were sitting untagged for want of a dimension check. Mismatched rows are now skipped and counted, with one message naming the way out.
- **Two concurrent "is the library busy?" checks no longer invent a holder on Windows.** `msvcrt` has no shared lock mode, so the peek probe was exclusive and overlapping peeks excluded *each other*; the loser reported a job that had already finished — the spurious 409 in the viewer that probing shared was introduced to remove, fixed on POSIX and still live here. The peek now retries the way the acquire side already did, with jittered backoff, since peeks arrive in phase.
- **Four standalone CLIs ran silently.** `tag_existing.py`, `calibrate.py`, `diagnostics.py` and `validate_db.py` each build a module logger and log freely, then never install a handler, so everything below WARNING was dropped. `tag_existing.py` tagged 26,451 photos in one run and printed nothing at all. They now share one `configure_cli_logging()` helper, which honours `FACET_LOG_LEVEL` and stays out of the way when a scan has already configured logging.

### Changed
- **A scan resolves each path once instead of three times.** Deduplication, the unscanned set and the todo-list filter each called `resolve()` over the same paths — invisible on a local disk, but every call is a filesystem round-trip on a NAS. Measured on an SMB library of 153,574 files: 3.94 ms cold and ~2 ms warm per call, so two of those passes were minutes of latency before a single photo had been read.
- **Cluster assignment is linear again.** Resolving a face's row position scanned a list — a membership test and an `.index()` call, each O(n), inside a loop over every clustered face. Doubling the face count multiplied the cost by 3.9–4.1×; a dict lookup is 750× faster at 16,000 faces.

Structure is stable, labelling is not, so auto-clustered person IDs must not be assumed to survive a re-run.
- **Scan output is readable again.** Hugging Face weight-loading bars were explicitly *enabled* and redrew on every model load; `open_clip` logs through the root logger where no logger name can reach it; `timm` and `pyiqa` announce every model they touch; and `topiq_nr_face` warned once per batch about photos with no face, which is expected rather than exceptional. Log records now also emit through `tqdm.write`, so a line arriving mid-scan no longer lands inside the progress bar's own line.

### Added
- **Corrections to a panorama can be made from the gallery and from culling, in both directions.** Geometry cannot recover intent, so a residual error rate is inherent — and each direction of error is found somewhere different. ## [1.10.0] "Aventurescence" — 2026-08-10

### Added
- **Panoramas are recognised as panoramas** (`--detect-panoramas`, `panorama_detection` config, `sequence_kind` values `panorama` and `hdr_panorama`, `is_sequence_lead` column). A sweep's frames were shot to be stitched, not to compete, but burst detection cannot tell: they arrive seconds apart from one camera at one focal length, so it grouped them as competing takes and hid all but one behind a lead chosen on a criterion that means nothing for a pan. On the 126k-photo library this was measured on, a confirmed 33-frame sweep was found **shredded across seven burst groups**. Nothing in stored metadata identifies a pan — one confirmed set was shot with locked exposure and another on auto — so the evidence is geometric: SIFT features and a RANSAC homography between consecutive frames, measured on the stored 640px thumbnails. No original decode, no model, no new dependency. What separates a sweep from a burst is *cumulative* drift rather than per-frame shift: real panoramas are shot at roughly 90% overlap, so one step moves only 5-18% of the frame, while over a run a burst wobbles around zero and a sweep marches. Requiring every pair to shift would instead have rejected every HDR panorama, whose frames hold still while the bracket fires. Thresholds were calibrated against 26 panoramas and 8 non-panoramas confirmed by eye rather than reasoned about; precision measured ~96%.
- **Culling can be browsed by panorama and by HDR panorama** (`GET /api/culling-groups?group_by=panorama|hdr_panorama`). Kept out of the merged `all` feed for the same reason brackets are. Every frame starts marked keep — a pan has no best frame, since each one covers a different part of the scene — and confirming one records no comparison pairs.
- **Sticky per-set corrections** (`POST /api/culling-groups/override_sequence`, `photo_sequence_overrides` table). Geometry cannot recover intent: a deliberate sweep and a pan that follows a moving subject are the same measurement, so a residual error rate is inherent. A correction says "this is not a panorama" or "these frames are one", and survives every later detection run — it lives in its own table because the detector clears and rewrites `photos.sequence_*` on each pass.
- **Panorama thresholds are editable from the viewer** (`GET|PUT /api/config/panorama_detection`, `POST /api/scan/detect_panoramas`). Editing a threshold changes nothing on its own, since detection is a batch pass rather than a live query, so the re-run is offered alongside it.
- **`hide_panoramas` gallery toggle**, showing one representative frame per sweep, mirroring `hide_brackets`.
- **A tile that stands for a whole set now says so.** With a hide toggle on, the other frames are collapsed behind one representative and nothing on the tile revealed it, so a 33-frame sweep read as a single landscape that happened to score well. The representative carries its kind as an icon with a tooltip, shown only while the matching toggle is actually hiding the rest of the set.
- **Star ratings are visible without hovering**, on the same terms as the favourite heart: a rating the user set is a standing fact about the photo. The persistent badges were also 6px off from the controls they stand for, which read as every icon jumping as the pointer entered or left a tile; each now occupies the exact box of its control.

### Fixed
- **A bracket run no longer wipes the labels of any other sequence kind.** `utils/sequence.py` cleared every labelled row rather than its own, so once a second kind existed each pass would silently delete the other's work on every run — invisibly, because each then re-created its own labels on the way out.
- **`hide_brackets` no longer hides frames that are not brackets.** It matched on a null-versus-set exposure offset, which is true of every panorama frame, so with the toggle on by default an entire sweep would have vanished from the gallery.

## [1.9.0] "Chatoyance" — 2026-08-10

### Added
- **Exposure brackets are recognised as brackets** (`--detect-sequences`, `sequence_detection` config, `sequence_group_id` / `sequence_kind` / `sequence_ev_offset` columns). Burst detection groups on framing and capture time, which describes a bracket exactly — so a bracket was collapsed into a burst, its lead picked by `aggregate`, and with the shipped `hide_bursts` default two frames in three disappeared behind whichever exposure happened to score best. On the 126k-photo library this was measured on, that was **226 sets, every one of them swallowed**. The ladder is now derived from the `f_stop` / `shutter_speed` / `ISO` already stored per photo, so an existing library is labelled by arithmetic alone — no rescan, no image decode, no model — and a group that turns out to be exactly one bracket has its lead moved onto the base exposure. Frames carry their exposure compensation signed the way a camera labels an AEB set, `-2` dark and `+2` bright. Panorama detection is deliberately not included: its frames share one exposure and differ by a pan, which wants its own evidence rather than a guess bolted onto this.

A bracket buys latitude the base exposure clips away; when that base clips neither shadows nor highlights there was nothing to recover. Sets whose base has never been measured are left alone — unmeasured is not unclipped.

Reuses the culling lightbox's pane wholesale, full-resolution swap past the fit scale included.

Deliberately independent of "Best of Burst" rather than relying on it — a quarter of real bracket sets share a burst group with unrelated frames, where the burst lead is not the base exposure and the flanking frames stayed on show. Measured on a 126k library: 549 frames hidden with burst-hiding off, and the hidden-photos banner counts them so "Show all" still reveals everything.
- **A weekly notice when a newer Facet has been released** (`GET /api/updates/check`, `updates` config block). Distinct from the browser's existing "a new version is available", which swaps the page onto a bundle it has already downloaded; this one is about a release nobody has installed yet. A failure is silent. Only edition users are told, since upgrading is an operator's job and no one else could act on it, and each browser shows the notice at most once a week. - **A docked details panel** (`tooltip_mode: "panel"`). The floating tooltip moves with the cursor, which makes comparing the same field across photos guesswork. It now falls back to a properly positioned floating tooltip, and the menu stops offering a mode the viewport cannot render.
- **The header navigation no longer shows a scrollbar when everything fits.** Each Material icon button hangs its 48px accessibility touch target 6px past its 36px box, and the scrolling container counted that decorative overhang as content: at 900px the icons occupied exactly the space available and the bar still scrolled. It still scrolls when the icons genuinely do not fit.

### Fixed

- **Pending rating syncs are flushed at shutdown rather than dropped.** The debounced timers that mint rating-derived comparison rows were never fired or disarmed when the server stopped, so a sync in flight was lost. It now runs bounded at five seconds on a daemon thread, after the checkpoint thread has stopped (so it doesn't contend for SQLite's single writer) and before the final truncating checkpoint (so its rows land in the database, not in a WAL the next start inherits).
- **The throughput benchmark measured the wrong process.** `peak_vram_mb` sampled Torch's allocator counters in the harness while the work ran in a subprocess, and those counters are process-local — so the figure was `0.0` on CUDA as much as on Metal, and had almost certainly never meant anything. GPU memory now comes from `nvidia-smi`'s per-process table filtered to the scoring child and its workers. Metal exposes no per-process equivalent, so no GPU figure is reported there at all: unified memory is system RAM, and the process tree's RSS is reported under its own name with the method stated beside it. A metric that could not be sampled reports as unavailable, never as zero. **Schema change**: `peak_vram_mb` is removed (not aliased); `peak_gpu_memory_mb`, `peak_rss_mb`, `gpu_memory_method` and `rss_method` replace it.

### Internal
- The retry helper's wall-clock budget, added in 1.8.0, gained the test it never had — it was covered only through an endpoint, so a regression to counting attempts would have gone unnoticed.
- CI installs `psutil`, a declared dependency its hardcoded subset had omitted, and the two tests that need `torch` or `psutil` skip cleanly where those are absent.

## [1.8.1] "Iridescence" — 2026-08-09

### Changed
- **The `auto` VRAM profile is sized from unified memory on Apple Silicon** instead of always resolving to `legacy`. There is no CUDA device-properties query for unified memory, so `auto` used to fall to the weakest tier on any Mac — a 128 GB machine included — even though the higher-tier models had just been taught to run on Metal. Thresholds are deliberately conservative, each covering the profile's model weights twice over and leaving 8 GB to macOS, then rounded up to a memory configuration Apple ships: 16 GB reaches `8gb`, 32 GB reaches `16gb`, 48 GB reaches `24gb`, and anything smaller stays `legacy`. An explicitly configured profile remains authoritative, and no fake VRAM figure is fed into the CUDA path. Whether the selected tier actually fits on Metal is unverified — it needs a Mac.
- **`PUT /api/config/scoring_contexts/{name}` now requires both `promote` and `excluded`**, and answers 404 rather than 400 for an unknown context. A partial body previously applied as a full replacement, so `{"promote": [...]}` silently cleared the exclusions; it is now refused with 422 and the config is left untouched. The shipped client always sent both fields, so no in-tree caller changes.

### Fixed
- **The library lock warns when it cannot do its job across hosts**: `flock` is host-local on SMB/CIFS, so two machines sharing an SMB-mounted database directory would each believe they hold it. The acquire now detects such a mount and says so once, without refusing — NFS between Linux clients gives real cross-host semantics and stays silent. Documented in [docs/DEPLOYMENT.md](docs/DEPLOYMENT.md).
- **`--upgrade-db` no longer runs its schema migration unlocked.** Step 0 issued `ALTER TABLE` on `photos` while holding nothing, so landing inside a recompute's long write transaction failed it and aborted the upgrade before it began. The DDL now takes the library lock and releases it before the subprocess chain, which takes its own.
- **Armed retrains are cancelled at shutdown** rather than left to fire. The accumulated counter is persisted, so the next rating re-arms; firing one as the process goes away would start a multi-minute train that cannot finish.

### Security
- **Rotating a password now revokes the tokens issued under it.** Nothing was invalidated server-side before: after a logout, after "Lock Edition", and even after `viewer.edition_password` was changed, an existing JWT still performed edition writes for its full 48 hours — so the interface offered a revocation that never happened. Tokens now carry a digest of the stored viewer and edition passwords: rotating the viewer password ends the session outright, and rotating the edition password drops edition rights while leaving the session intact. Logout remains a client-side token drop, which the code and the client now state plainly instead of implying otherwise. **Every existing session is signed out once on upgrade**, since tokens issued before this carry neither claim.
- **One mutex now guards `scoring_config.json`.** Two lock families protected the same file — the config writers used one, the password upgrade and the share-secret initialisation another — so interleaved writes could lose one side's update wholesale.

- **Facet → Immich sync** (`--immich-sync`, `--immich-test`): push Facet star ratings and favorites to an Immich server over its REST API (`x-api-key`), resolving assets by `originalPath` through configurable path-prefix mappings with a single bulk search pass. Ratings follow Immich's version-safe policy (1–5 only, never 0/−1); an optional top-picks album collects photos above a rating threshold. `--immich-sync` honors `--dry-run` (resolves but never writes) and `--user` (per-user ratings overlay). REST-only — no Immich database coupling. Configured via the `immich` block.
- **Client proofing on shared albums** (`viewer.features.show_proofing`, off by default): a shared-album link can run in proofing mode where the client (no account) exchanges the share token — plus an optional `viewer.proofing.pin` — for a short-lived session, then hearts photos and leaves comments. Picks live in a dedicated `album_client_picks` table, bounded server-side to that album's photos and fully isolated from the owner's ratings (they never touch `photos.is_favorite` / `user_preferences` and never train the personal ranker). The owner reads them from an edition-gated dialog on the album card.
- **Per-face eyes-open and smile scores** persisted on every face row: a continuous eyes-open score and a new geometric smile score (mouth-corner lift, roll-invariant), computed at scan time from the stored 106-point landmarks and backfillable with `--recompute-face-signals`. The culling darkroom's face panel colour-codes each crop green / orange / red and adds live eyes / smile threshold sliders; the blink and expression cut-offs are now the config keys `face_detection.eyes_closed_max` / `poor_expression_min`.
- **Explainable form and colour-harmony metrics**: five CPU-only signals — left-right symmetry, visual balance, edge-orientation entropy, box-counting fractal complexity, and a Matsuda hue-template colour-harmony score over a k-means palette — computed at scan time and backfillable with `--recompute-form`. They surface in the critique breakdown, suggestions and the photo tooltip, and are available as category weights (shipped at 0 %, so existing aggregates are byte-identical until you opt in).
- **Zero-shot distortion attributes and skin-tone naturalness** in the critique (advisory, no aggregate coupling): `--recompute-distortions` labels each photo with likely defects (motion blur, colour cast, oversharpening, …) via ExIQA-style contrastive prompts over the stored embedding, and prints a correlation report against `liqe_score` / `noise_sigma`; `--recompute-skin-tone` flags portraits whose skin chroma drifts green / magenta / blue / yellow (CIEDE2000 vs a CCT skin locus). Both render in the critique dialog as warning chips and a skin-tone note.
- **True fullscreen** for the culling darkroom: a header toggle and the `F` key drive the Fullscreen API so review runs edge-to-edge; the key is listed in the shortcut legend.
- **Structured VLM critique**: the AI critique (16 GB / 24 GB profiles) now uses a configurable ladder prompt (`critique.vlm`) injecting the full rule breakdown, penalties and EXIF, rendered as Observation / Assessment / Suggestions. The result is cached per photo (`refresh` regenerates), translated on demand, and generated against the stored thumbnail so RAW files no longer fail silently.
- **Brazilian Portuguese caption / critique translation** (`pt`, via `opus-mt-tc-big-en-pt`), completing the six-language set.

### Changed
- Concurrent VLM generate calls (critique and captioning share one cached model) are serialized behind a lock instead of racing the GPU.
- The three stored-landmark backfills (blink, eyes/expression, face signals) share one iteration scaffold; the auto-cull and album-fill paths reuse the shared reviewed-flag and album-append helpers.
- Scan-time form metrics resize with `reducing_gap`, and the thumbnail / embedding recompute paths stream row-by-row instead of loading the whole library into RAM (avoids OOM on large libraries).

### Fixed
- **Data loss on re-scan**: re-scoring an already-scored photo (`--force`, `--retry-failed`, watch mode) went through `INSERT OR REPLACE`, which deletes and re-inserts the row — silently cascade-deleting its faces, comparisons, learned scores and per-user ratings and resetting star ratings, favorites, captions, moments and the VLM critique, and corrupting the full-text search index. Both save paths now UPSERT, so a re-scan preserves all user and derived data and keeps search consistent.
- **Security (anonymous access)**: an unauthenticated request was served every photo (and download) even in multi-user mode or with a viewer password set, because the visibility filter fell open to "all photos". It now returns nothing unless the install is genuinely open (single-user, no password).
- **Security (committed secret)**: the JWT signing secret shipped in the tracked `scoring_config.json`; it is now blank and generated per install on first run. Existing deployments should let it regenerate (delete the `share_secret` value).
- **Security (proofing)**: a share-client session token was accepted across the entire API through `get_optional_user`, so on the default empty-`edition_password` setup a shared-album link escalated to full edition access (mass reject, file move / trash). The token now authenticates nothing but its own picks routes. The PIN check is rate-limited against brute force, live sessions stop working the moment an album is unshared or proofing is disabled, and secret comparison is byte-safe.
- `--score-topiq` / `--recompute-tags` crashed with an `UnboundLocalError` on `tqdm`; the database validator flagged every photo of a SigLIP library as corrupt (hardcoded to the CLIP embedding size); full-text search came back empty after a schema upgrade until a manual rebuild; and `--optimize-weights` categorized photos differently from production because it could not parse fractional shutter speeds. All fixed.
- The VLM critique path was dead with the shipped config — it gated on a non-existent `models.vlm_tagger` block and the raw `vram_profile` value ("auto"), so `mode=vlm` always returned unavailable. It now resolves the active profile like the caption endpoint.
- `--recompute-colors` and `--recompute-ocr` crashed with a `NameError` (a later local `import tqdm` shadowed the module in the recompute helper).
- The incremental viewer-database export no longer wipes the GPU-expensive VLM-critique cache with NULLs, and now propagates the new per-face eyes / smile columns.

## [1.0.0] — 2026-03-17

### Scoring & Analysis
- Multi-dimensional scoring: aesthetic, composition, sharpness, exposure, color, face quality, eye sharpness, noise
- TOPIQ IQA (0.93 SRCC), with TOPIQ IAA, TOPIQ NR-Face, and LIQE as supplementary quality metrics
- SAMP-Net composition pattern detection (14 patterns: rule of thirds, golden ratio, vanishing point, symmetry, …)
- BiRefNet subject saliency: sharpness, prominence, placement, and background separation per photo
- CLIP ViT-L-14 (8 GB) and SigLIP 2 NaFlex SO400M (16/24 GB) embedding profiles
- VRAM auto-detection with four profiles: legacy / 8 GB / 16 GB / 24 GB
- Percentile normalization — 90th-percentile maps to 10.0 regardless of library size

### Categories & Weights
- 17 content categories with per-category scoring weights (portrait, landscape, wildlife, macro, street, …)
- Config-driven category determination via `filters` (numeric ranges, booleans, tags) and `modifiers` (bonus/penalty)
- A/B weight comparison: tune weights, preview score changes against a snapshot, apply or discard
- `--compute-recommendations` analyses the database and suggests scoring fixes

### Culling
- Burst detection groups similar photos taken within a configurable time window
- Best-of-burst selection surfaces the top-scoring frame per group
- Blink detection flags closed-eye portraits
- Duplicate detection via perceptual hash (pHash)
- AI similarity culling groups visually similar photos for manual review (`/api/similar-groups`)

### Face Recognition
- InsightFace buffalo_l detection with 106-point landmarks
- HDBSCAN face clustering into named or auto-labelled persons
- Merge suggestions UI with similarity threshold slider and one-click batch merge
- Incremental and force-reprocess modes for extraction and clustering
- Per-face and per-person thumbnails stored in SQLite

### Gallery & Browse
- Gallery modes: mosaic, grid, list
- Real-time filter panel: score, date, camera, lens, aperture, focal length, tag, person, category, composition pattern, GPS radius, Top Picks
- Semantic text-to-image search via CLIP/SigLIP embeddings
- Timeline view with year → month → day drill-down and mini-calendar heatmap
- Map view with marker clustering (Leaflet), GPS filter dialog with radius picker
- Folders browser with breadcrumb navigation and directory cover photos
- Memories — "On This Day" photos from previous years
- Slideshow with per-capsule transitions (crossfade, slide, zoom, Ken Burns)
- Capsules — 30+ AI-curated themed collections: journeys, seasonal, golden, faces of, color story, progress, person pairs, and more
- Albums: manual and smart (filter-based), with sharing via tokenised links

### Organize
- Star ratings and favorites per photo
- Batch tag/rate/favorite/delete operations
- AI captions (VLM-generated) with automatic translation via MarianMT
- Tags from CLIP similarity (8 GB) or Qwen VLM (16/24 GB)
- `photo_tags` lookup table for 10–50× faster tag filtering at scale
- GPS extraction from EXIF into the database; reverse geocoding via `reverse_geocoder`

### Statistics & Understand
- Statistics dashboard: score distribution, top cameras/lenses, composition breakdown, category split
- Per-category weight editor with live recompute
- AI critique: rule-based score breakdown (all profiles) or VLM-powered critique (16/24 GB)

### Web Viewer
- FastAPI backend + Angular 20 zoneless signal-based SPA on port 5000
- Dark/light theme with 10 accent colours; responsive layout
- 5 languages: English, French, German, Spanish, Italian
- Multi-user mode with role-based access (admin / viewer) and per-user ratings
- Edition password for single-user locking
- Photo detail page with EXIF, GPS chip, face chips, clickable tags/persons, caption edit
- Scan trigger from the web UI
- Photo download and CSV/JSON export
- Plugin/webhook system for post-scan automation

### Infrastructure
- SQLite with WAL mode, mmap, and statistics cache (`stats_cache` table, 5-minute TTL)
- RAW support: CR2, CR3, NEF, ARW, RAF, RW2, DNG, ORF, SRW, PEF (via rawpy + exifread)
- Multi-pass GPU scheduling — no inter-batch idle time; single-pass available for high-VRAM setups
- `--doctor` diagnostic command (Python, GPU, deps, config, database)
- `--dry-run` preview mode — scores a sample without writing to the database
- Deployment guides for Linux, Synology NAS, and Docker

### Quality
- 267 automated tests across 20 test files (Python pytest + FastAPI TestClient)
- LIKE wildcard escaping in all path-prefix SQL filters
- No silent `except` blocks — all errors logged via Python `logging`
- CodeQL SSRF alerts resolved
