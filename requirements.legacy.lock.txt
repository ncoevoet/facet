# Sticky, tested-working dependency lock for the LEGACY CUDA Docker image
# (the `-cuda-legacy` tag), built on pytorch/pytorch:2.6.0-cuda12.6-cudnn9-runtime.
# That base's torch ships sm_50...sm_90 cubins, so this is the variant for
# Maxwell, Pascal and Volta cards; Blackwell (sm_120) needs the CUDA 12.8 base
# and requirements.lock.txt instead (issue #119). The Dockerfile picks between
# the two locks with REQUIREMENTS_LOCK, set per variant in docker-publish.yml.
# Container-validated at transformers 5.15.0 on 2026-08-13: a 16gb-profile GPU
# container built from this exact lock scanned 63 photos with 0 errors, and
# build-tools/verify_scan_db.py passed (embeddings, VLM tags, aesthetic,
# saliency, faces, moments all populated and in range).
# Pin discipline learned the hard way: torch 2.6.0 pins sympy==1.13.1 exactly;
# any drift here makes pip swap the base image's torch/CUDA stack (a stray
# sympy==1.14.0 pulled in torch 2.13 + CUDA 13 before it was caught). It is also
# why the two CUDA bases cannot share one lock file: torch 2.11.0 requires
# sympy>=1.13.3, which the pin below violates.
# The cuML layer installed AFTER this lock intentionally downgrades
# numba/llvmlite/pandas/pyarrow — the container's final versions for those four
# differ from these pins by design; do not "fix" them from a container freeze.
# torch/torchvision + nvidia-*/triton are intentionally omitted — the CUDA base image
# (pytorch/pytorch:2.6.0-cuda12.6-cudnn9-runtime) already provides them.
# Regenerate: docker compose ... exec facet pip freeze --all | (filter base-image pkgs)
