## 启动查看器

### 生产环境

```bash
python viewer.py
# 打开 http://localhost:5000
```

它会在同一个端口上同时提供 API 和预编译好的 Angular 应用。

若需要更高吞吐量，请以生产模式运行（Uvicorn，不自动重载）。添加 `--workers N` 可横向扩展（默认为 1）：

```bash
python viewer.py --production --workers 4
```

### 开发环境

分别启动 API 服务器和 Angular 开发服务器：

```bash
# 终端 1：API 服务器
python viewer.py
# API 位于 http://localhost:5000

# 终端 2：带热重载的 Angular 开发服务器
cd client && npx ng serve
# 打开 http://localhost:4200（API 调用会代理到 :5000）
```

## 身份验证

### 单用户模式（默认）

通过配置启用可选的密码保护：

```json
{
  "viewer": {
    "password": "your-password-here"
  }
}
```

设置之后，用户必须先通过身份验证才能访问查看器。可选的 `edition_password` 用于开放人物管理和比较模式。

登录时还会把会话令牌镜像写入一个 `HttpOnly`、`SameSite=Lax` 的 Cookie，这样那些无法携带 `Authorization` 请求头的浏览器原生请求（加载缩略图的 `<img>` 标签、扫描进度流）在已加锁的部署上也能通过验证。该 Cookie 仅对只读请求（GET/HEAD）生效；任何会改变状态的调用仍然要求 Bearer 令牌，因此不会增加 CSRF 攻击面。退出登录会调用 `POST /api/auth/logout`，该接口会清除此 Cookie。

### 多用户模式

适用于家庭 NAS 场景，每位成员都有各自的私有照片目录。在 `scoring_config.json` 中添加 `users` 段即可启用：

```json
{
  "users": {
    "alice": {
      "password_hash": "salt_hex:dk_hex",
      "display_name": "Alice",
      "role": "superadmin",
      "directories": ["/volume1/Photos/Alice"]
    },
    "bob": {
      "password_hash": "salt_hex:dk_hex",
      "display_name": "Bob",
      "role": "user",
      "directories": ["/volume1/Photos/Bob"]
    },
    "shared_directories": [
      "/volume1/Photos/Family",
      "/volume1/Photos/Vacations"
    ]
  }
}
```

用户只能通过 CLI 创建（没有注册界面）：

```bash
python database.py --add-user alice --role superadmin --display-name "Alice"
```

完整参考见[配置](CONFIGURATION.md#用户)。

### 角色

| 角色 | 查看自己的 + 共享的 | 评分／收藏 | 管理人物／人脸 | 触发扫描 |
|------|:-:|:-:|:-:|:-:|
| `user` | 是 | 是 | 否 | 否 |
| `admin` | 是 | 是 | 是 | 否 |
| `superadmin` | 是 | 是 | 是 | 是 |

### 照片可见性

每位用户能看到自己所配置目录中的照片，外加共享目录中的照片。所有端点都会强制执行可见性规则：照片库、缩略图、下载、统计、筛选项以及人物页面。

### 按用户存储的评分

在多用户模式下，星级评分、收藏和淘汰标记按用户存储在 `user_preferences` 表中。每位用户独立评分——Alice 的收藏不会影响 Bob 看到的内容。

迁移已有的单用户评分：

```bash
python database.py --migrate-user-preferences --user alice
```

### 我的偏好

这是一个一等公民级别的排序选项，背后是个人排序模型的 `learned_score`（原名“Picked for you”）。它会按模型从你的 A/B 比较、评分和选片决定中学到的偏好来排列照片。排序旁边的置信度徽章显示已学习覆盖率（有学习评分的照片占比）以及模型在留出集上的准确率，方便你判断该在多大程度上信任这个排序。用 `python facet.py --train-ranker` 训练或刷新该模型。

由 `viewer.features.show_my_taste` 控制（默认：`true`）。模型状态通过 `GET /api/ranker/status` 暴露。

## 照片库功能

### 照片卡片

- 带评分徽章的缩略图
- 可点击的标签，便于快速筛选
- 已识别人脸的人物头像
- 类别徽章

### 多选与批量操作

- 点击照片选中，Shift+点击可范围选择
- 出现操作栏，显示已选数量和可用操作
- **收藏**——把所有选中照片标为收藏（并清除淘汰标记）
- **淘汰**——把所有选中照片标为淘汰（并清除收藏和评分）
- **评分**——为所有选中照片设置星级（1–5），或清除评分
- **添加到相册**——把所选照片加入已有相册或新建相册
- **全选**——在没有任何选中项时，选中整个筛选后的视图——当前筛选条件匹配的每一张照片，而不仅仅是无限滚动已经取回的那几页——且不产生任何网络开销：服务器只有在真正执行批量操作时才根据筛选条件推导出行集合。若已经选中了一张或多张照片，则只扩大到当前已加载的照片，并由横幅提示可进一步扩大到整个视图。无论哪种方式，对整个视图执行操作前都会先弹出确认对话框，说明确切的照片数量。
- **反选**——把选择集换成它的补集。在没有任何选中项时，补集就是整个筛选后的视图，与上面的“全选”完全一致，同样不发起请求——此前这里的措辞正是在这一点上出了错。在已有选中项时，反选仍然限定在已加载的照片范围内：先挑出要保留的，再反选，再淘汰——这是在完全不触及你尚未看过的照片的前提下，最直接地看清哪些照片即将被处理的方式。
- **比较**——把 2–4 张选中照片并排打开，平移和缩放保持同步（滚轮缩放、拖拽平移、双击复位；所有窗格一起移动，超过适配比例后会切换到全分辨率）。这与选片暗房使用的是同一个视图，但现在任何手工挑选的照片集都能用，而不再只限于连拍中相邻的帧。
- **复制文件名**——把选中照片的文件名复制到剪贴板；整个视图的复制会先确认，超过 10 000 张照片的视图会被直接拒绝，而不是复制一部分
- **导出**——在选中文件旁写入 XMP 附属文件（星级／收藏／淘汰）（参见[导出到后期软件](#导出到后期软件)）
- **选片后导出／清理**——把保留照片复制、或把淘汰照片移动／移入回收站到目标文件夹（参见[选片后导出／清理](#选片后导出清理)）
- **下载**——下载选中的照片
- 按 Escape 键或“清除”按钮可清除选择

批量操作需要编辑模式。双击任意照片可直接下载它。

### 保留前 N%

照片库工具栏中的 **保留前若干 %** 控件（编辑模式）可以把整个筛选后的视图变成一步到位的选片。设定一个百分比，服务器就会按**当前排序**（综合评分、我的偏好、精选照片、清晰度……）对当前视图排序，保留排在前面的那一部分，并**选中其余照片**——也就是排名最靠后的那些——这样你就能从选择操作栏里把它们淘汰（或者先取消选中想要留下的照片）。不会移动或删除任何文件：它只是填充选择集（而每一次淘汰同样会训练“我的偏好”）。选择集上限为 5000 张照片；视图过大时控件会明确说明——请缩小筛选范围（相册、日期、人物……）再处理剩下的部分。排序运行在与照片网格相同的、已应用隐藏筛选的视图上，因此在默认的 `hide_brackets` / `hide_panoramas` 之下，一组包围曝光或一组全景照片在百分比中只算**一张**照片，而不是每帧各算一张。

### 选片后导出／清理

批量操作栏中的**选片后导出／清理…**对话框（编辑模式）可以一步把保留照片复制、或把淘汰照片移动／移入回收站到目标文件夹（移入系统回收站受 `viewer.cull.allow_trash` 控制，且永远不是永久删除）。应用操作在设计上就是安全的：`POST /api/cull/apply` 从不轻信客户端提交的删除清单——它会在服务端根据每张照片自己的 `is_rejected` 状态重新推导出本次操作真正的目标集合（复制只作用于保留照片，移动／回收站只作用于淘汰照片），并把范围之外的一切计入 `excluded_by_state` 而不去处理它们。每次调用默认都是试运行，因此在写入任何内容之前一定会先跑一次预览，移动／回收站操作必须显式传 `dry_run=false` 才会执行；把淘汰照片那份未被触碰的 RAW 或附属文件也一并带上则需要主动开启（`include_companions`），因此淘汰一张派生出来的 JPEG 绝不会悄悄连它的 RAW 一起带走。已有多款商业照片工具出现过“删除所选”作用到错误照片的缺陷；Facet 的 apply 端点在设计上就不允许客户端直接指定删除集合。

**“将淘汰照片移入回收站”的可用性。**只有当 `GET /api/config` 报告 `cull.trash_available: true` 时——即 `viewer.cull.allow_trash` 已开启**并且** `send2trash` 包可导入——“将淘汰照片移入回收站”单选项才会出现，而不是让对话框提供一个服务器会拒绝的操作。直接调用 `POST /api/cull/apply` 并带上 `action=trash_rejects` 时，仍可能分别撞上这两种拒绝：`403` 表示 `scoring_config.json` 中的 `viewer.cull.allow_trash` 处于关闭状态；`400` 表示配置允许，但当前环境没有安装 `send2trash`。对话框不再把两者混为一谈：本该出现单选项的位置会说明原因——`allow_trash` 已开启但缺少软件包时显示“未安装 send2trash 软件包”，其他情况显示“管理员已禁用回收站功能”——因此无需调用 API 就能区分两者。能力状态未知时（`/api/config` 未加载，或字段缺失）一律按禁用处理，因为“未知”不足以成为提供破坏性操作的理由。

**多帧照片组。**在默认的 `hide_brackets` / `hide_panoramas`（两者均开启）之下，本对话框所依据的照片库选择集只包含包围曝光的基准曝光帧，或全景组中被标记的中间帧——所以按默认设置用这种方式处理一组 HDR 包围曝光或一次全景扫拍时，被复制、移动或移入回收站的是那**一个**代表文件，绝不会波及整组其余照片。有两个彼此独立的可选复选框可以扩大处理范围：**包含配套的 RAW／XMP 文件**（`include_companions`）会带上*同一*帧的同名 RAW 和 `.xmp` 附属文件；**包含同组其他照片**（`include_sequence_siblings`）会带上与匹配照片共享 `(sequence_kind, sequence_group_id)` 的*所有其他*帧——也就是照片库正隐藏起来的那些包围曝光档位或全景拼接帧——**前提是该同组照片自身的保留／淘汰状态与本次操作相符**。淘汰一次扫拍中的某一张并勾选此项，会移动或移入回收站的是那一张以及该组中其他同样被淘汰的帧，绝不会碰你保留下来的那些；状态不符的同组照片会被计入 `excluded_by_state`。你主动从选择集中移除的帧绝不会又被当作同组照片拉回来：`exclude` 对同组照片的处理与对目标集合的处理完全一致，因此被排除的帧既不会出现在被操作的文件里，也不会计入 `sequence_siblings`。即便复选框未勾选，预览也会报告存在多少张同组照片（`sequence_siblings`），因此一组照片的存在绝不会被悄悄隐去；而 `matched` 则用来区分“选择集中没有任何照片符合本次操作的条件”和结果为空这两种情况。移动或回收全景／包围曝光组的代表帧时，会从存活下来的同组照片中重新挑一张作为新的 `is_sequence_lead`，这样在默认的隐藏开关下该组之后仍然可见——这是这个原本只涉及文件的端点唯一一次写数据库。若想手工挑选一组中的部分照片，而不是全有或全无，请先通过照片详情中的“在照片库中打开此照片组”操作打开它——该照片组作用域筛选生效期间会屏蔽全部四个隐藏开关，因此每一帧都可以单独选中。直接调用 `POST /api/cull/apply` 并带上 `filters` 请求体则会完全绕开查看器自身的默认值：决定同组照片处理前作用域的是调用方自己的 `filters.hide_brackets` / `filters.hide_panoramas`，而不是 `viewer.defaults`。不过除这两个隐藏标志之外，`filters` 不再单独解析：未设置的字段会与 `GET /api/photos` 一样回退到查看器自身的排序／类型／人物／每页数量默认值，而基于内容的**照片类型**选择（例如 `type=landscape`）会展开成该类型完整的底层筛选条件集——因此一个 `filters` 请求体与它所复制自的照片库视图会解析出相同的行集合。此前选片和导出都跳过了这一步，导致由照片类型驱动的视图通过 API 解析出的行集合可能与网格中显示的不一致。匹配超过 10 000 张照片的 `filters` 请求体会被直接拒绝（`412`，并给出数量和上限），而不是被截断；这个上限对试运行和真实执行同样适用——把你以为是完整的视图只处理了一半，比一次明确的拒绝更糟糕，而且预览也不能被拿来完成执行本身被拒绝去做的无界工作。请缩小筛选范围（相册、日期、人物……）后重试。

**可以写入哪里。**在未配置 `viewer.export.allowed_target_dirs` 时，Facet 唯一会写入的文件夹就是你的扫描目录——把对话框指向照片树下的某个子文件夹（例如 `_rejected`）即可开箱即用。若要使用扫描树之外的文件夹，请先把它加入 `viewer.export.allowed_target_dirs`；其他任何路径都会被拒绝并返回 `403`，与文件系统权限无关。参见[配置——导出与选片目标目录](CONFIGURATION.md#导出与选片目标位置)。在 Docker/Podman 中运行时，你输入的路径是**在容器内部**、针对实际挂载到那里的内容解析的，绝不是针对宿主机文件系统——参见[部署——容器路径语义](DEPLOYMENT.md#容器路径语义)。

**每个操作都提示“拒绝访问”。**那是 `403`——来自上面那道目标文件夹检查的刻意拒绝，或是编辑会话已过期——而不是文件系统或容器用户的权限问题。提示条不会说明是哪一种，请在浏览器的“网络”面板中查看失败请求响应体里的 `detail` 字段。真正的文件系统／权限问题表现不同：操作会报告部分成功并带上非零的 `errors` 计数，而不是整体失败，同时服务器会为每个失败的文件记录底层的操作系统错误。

### 显示选项

- **布局模式** - 在**网格**（大小一致的卡片）和**拼贴**（保留原始宽高比的对齐行）之间切换。拼贴仅限桌面端；移动端始终使用网格。
- **缩略图大小** - 调整卡片／行高的滑块（120–400px，保存在 localStorage 中）
- **隐藏照片详情** - 隐藏卡片上的照片元数据（仅网格模式）
- **提示信息** - 照片详情的显示方式：**悬停**（默认）、**点击**、**关闭**或**侧边面板**。侧边面板把同样的详情停靠在右侧抽屉中，而不是跟随光标，因此同一个字段在不同照片之间始终位于同一位置。它同时响应悬停**和**点击，因此在悬停永远不会触发的触摸屏上也能使用；光标离开网格时它会保留最后一次悬停的照片，而不是清空。它与筛选侧边栏共用同一个抽屉——打开筛选条件会把它隐藏，直到你重新关闭筛选，而网格宽度始终与打开筛选时完全一致。需要至少 1280px 的视口宽度。
- **隐藏闭眼照片** - 过滤掉检测到闭眼的照片
- **连拍最佳照片** - 每组连拍只显示评分最高的一张
- **包围曝光最佳照片** - 每组检测到的包围曝光只显示基准曝光帧，隐藏两侧的帧。**默认开启。**它与“连拍最佳照片”相互独立：约四分之一的包围曝光组与无关帧共处同一个连拍分组，而该连拍的代表帧并不是基准曝光帧，因此仅靠连拍隐藏会让多余的曝光帧留在画面上。
- **全景组最佳照片** - 每组检测到的全景或 HDR 全景只显示被标记的代表帧（中间帧），隐藏该次扫拍的其余照片。**默认开启。**
- **无限滚动** - 照片随滚动逐步加载
- **快速滚动（虚拟化）** - 按行开窗渲染：只有视口附近的
  行会存在于 DOM 中，因此在数万张照片中深度滚动
  依然流畅。默认开启；若遇到布局问题，可在筛选侧边栏的
  “显示”分区中关闭（网格模式且显示详情时始终使用完整
  渲染，因为那种情况下行高不确定）。该设置保存在
  localStorage 中（`facet_virtual_scroll`）。

### 相似照片

点击任意照片上的“相似”按钮，选择一种相似度模式：

- **视觉相似度**（默认）——pHash 汉明距离（70%）+ CLIP/SigLIP 余弦相似度（30%）。没有 pHash 时退回到仅使用 CLIP。
- **色彩**——直方图交集（70%）+ 饱和度距离（10%）+ 亮度距离（10%）+ 黑白加分（10%）。会先按黑白标记和饱和度范围预筛选。
- **人物**——查找包含同一（或同几位）人物的照片。可用时使用 `person_id`（速度快），否则退回到人脸嵌入向量的余弦相似度。

用**相似度阈值滑块**（0–90%）控制匹配的严格程度（人物模式下不显示）。结果较多时该面板支持无限滚动。

## 全景照片与包围曝光

全景照片的各帧是为了拼接而拍的，包围曝光的各帧是为了合成而拍的，
因此两者都不是一组互相竞争的照片。连拍检测无法区分它们
——这些帧都来自同一台相机、同一个焦距，相隔几秒钟——所以
若不做处理，它就会把它们归为一组，并按一条对全景扫拍毫无意义的
标准挑出代表帧，把其余的全部隐藏起来。

**在照片库中。**`包围曝光最佳照片`和`全景组最佳照片`（默认
均开启）会把每一组收拢到一张代表帧之后：包围曝光取基准
曝光帧，全景取中间帧。该帧会在底部一行、星标和爱心旁边带一个
小图标，说明它代表的是什么——普通扫拍、HDR 扫拍还是包围
曝光——并附有提示文字。只有当对应的开关确实正在隐藏该组
其余照片时，图标才会出现；开关关闭时每一帧都以自身身份出现在
屏幕上，也就无需谁来代表谁了。

**在选片中。**粒度菜单把`包围曝光`、`全景`和
`HDR 全景`作为各自独立的列表提供，绝不并入`全部`——重点就是要
把它们和本会被误读成的连拍分开来看。每一帧一开始都被标为保留，
确认一组时不会记录任何比较对：在一组曝光阶梯中偏好某一档、或在
一次扫拍中偏好某一帧，描述的是这组照片是怎么拍的而不是照片本身，
把它喂给排序模型会让之后的每一次排序都产生偏差。

**修正一组照片。**几何信息无法还原拍摄意图——一次有意的扫拍和
一次跟随移动主体的摇摄在测量上完全相同——因此残余的错误率是
固有的，实测约为 4%。一次修正（“这不是全景”
／“这几帧是一组”）是持久的：它存放在自己的表中，能够挺过之后
每一次检测运行，而检测运行会清除并重写它自己产生的标签。

两种错误方向各有各的操作入口，因为它们是在不同的地方被发现的。
**误报**在选片页面修正，因为那时这一组照片就摆在你面前：分组的
操作栏带有一个修正菜单（仅编辑模式），提供*不是全景*以及在普通与
HDR 之间重新标注。**漏检**则从照片库修正，因为未被检测到的扫拍
根本不会出现在任何选片分组里：选中这些帧，在选择栏中使用
*标记为照片组* → *标记为同一组全景照片*。两者都可以从提示条撤销，
且都至少需要两帧。

没有任何标注会立即生效。修正会立刻保存并标为待应用——
照片库图块上会出现一个时钟徽章，选片分组上会出现*修正待应用*标签
——因为检测是一次覆盖整个照片库的批处理，代价远高到无法每点击
一次就跑一遍。选片页面会显示一条横幅统计有多少修正在等待，旁边配有
**重新运行检测**按钮；侧边栏的*全景识别修正*筛选条件
（仅编辑模式，位于“细化”之下）会在整个照片库范围内列出它们，可按
任一方向或两者一起筛选。在那次运行之前，被抑制的一组仍会被当作全景
分组，被强制标记的一组仍未成组——修正是给检测器的一条备注，本身
并不是标签。

**调优。**“比较”页面下的“全景”标签页暴露了那些真正针对已标注
照片组校准过的阈值——最少帧数、最小扫拍幅度、
最长间隔以及 HDR 曝光跨度。保存它们本身不会改变任何东西：
检测是覆盖整个照片库的批处理而不是实时查询，因此该
标签页在保存按钮旁边还提供了重新运行。完整配置块参见
[CONFIGURATION.md](CONFIGURATION.md#全景检测)。

## 触发扫描（Superadmin）

当 `viewer.features.show_scan_button` 为 `true` 且用户具有 `superadmin` 角色时，照片库为空的状态下会出现一个**扫描照片以开始使用**按钮。它在 `scoring_config.json` 中出厂设置为 **`false`**（需超级管理员主动开启）。该按钮会打开扫描启动器对话框（`ScanLauncherComponent`）。

- 从启动器的列表中选择一个目录，直接在应用内开始扫描
- 启动器会把实时进度（SSE，并自动回退到轮询）推送到一个由结构化 `progress` 字段驱动的 `mat-progress-bar`，另外还有一段输出日志尾部，扫描结束时会刷新照片库
- 扫描以后台子进程（`facet.py`）方式运行；同一时间只允许一个扫描（全局锁）
- 目录选项来自 `get_all_scan_directories()`，它会合并每位用户的 `directories`、共享目录、`path_mapping` 目标以及独立的 `viewer.scan_directories` 列表——请为后者填入初始值（例如 `/data/photos`），这样单用户／Docker 安装才有可选的目标

当查看器运行在拥有 GPU 算力的同一台机器上时，这一功能很有用。

另有一个相关但独立的触发器 `POST /api/scan/recompute`，它复用同一把作业锁来原地重新为已有照片评分（不引入新文件）——参见[类别优先级与拍摄场景评分方案](#类别优先级与拍摄场景评分方案)。与这个仅限超级管理员的扫描按钮不同，它受编辑模式限制。

## 语义搜索

混合搜索，把 CLIP/SigLIP 嵌入向量相似度（70%）与基于照片描述和标签的 FTS5 BM25 文本匹配（30%）结合起来。输入诸如“群山之上的日落”或“在雪中玩耍的孩子”这样的查询，查看器就会按综合得分排序返回匹配的照片。

- 需要已存储的 `clip_embedding` 数据（在评分过程中计算）
- 安装了 sqlite-vec 时用它做 KNN 向量检索，否则退回到内存中的 NumPy
- 对 AI 照片描述／标签做 FTS5 文本检索，提供额外的关键词匹配（运行 `database.py --rebuild-fts` 启用）
- 使用与当前 VRAM 配置档相同的嵌入模型（16gb/24gb 用 SigLIP 2，legacy/8gb 用 CLIP ViT-L-14）
- `scope=text` 会把查询限制为对 OCR／描述文本的字面 FTS5 匹配，并跳过嵌入向量检索
- 由 `viewer.features.show_semantic_search` 控制（默认：`true`）

### 智能相册

把一组筛选条件（相机、标签、人物、日期范围、评分阈值等）保存为智能相册。随着新照片符合已保存的筛选条件，智能相册会动态更新。筛选条件组合以 JSON 形式存储在 `smart_filter_json` 中。

### 拍摄场景评分方案

每个相册都可以带一个拍摄场景评分方案，决定其成员照片由哪个类别胜出，与全局优先级顺序无关——参见[拍摄场景评分方案](CONFIGURATION.md#拍摄场景评分方案)。`PUT /api/albums/{id}/scoring_context`（受编辑模式限制）用于设置它，并把同一个方案落到**此刻**属于该相册的每一张照片上；响应中的 `conflicts` 统计已经带有不同方案的非手动成员数量，`manual_skipped` 统计其自身手动覆盖被原样保留的成员数量（相册指派绝不会悄悄把照片的手动覆盖转换成来自相册的设置），`updated` 则统计实际写入了多少张。手动相册按 `album_photos` 行解析成员；智能相册没有这些行，因此改为对实时数据库求值它保存的 `smart_filter_json` 来解析成员。那是相册的**筛选定义**，而不是“照片库当时恰好显示的内容”：它有意忽略照片库的隐藏闭眼／隐藏连拍／隐藏重复／隐藏淘汰这些视图偏好（它们是全局的、可在运行时切换的，且不属于 `smart_filter_json`），因此在这些开关打开时，`updated` 完全可能超过该相册自己的照片库视图所显示的照片数量——而当筛选条件当前什么都匹配不到时，它会返回 `updated: 0` 和一条 `warning`。无论哪种情况，这个落标都是一次性快照而不是实时订阅：手动相册在*之后*加入的照片确实会自动继承该方案，但智能相册的筛选条件在*之后*匹配到*新*照片时**不会**追溯地给它套上该方案——必须重新 `PUT` 一次才能纳入新的匹配项。`DELETE /api/albums/{id}/scoring_context`（在对话框中表现为“清除方案”操作，与选择 `default` 方案不同，后者是落上 `default` 而不是清除）会把这个相册所落的标恰好从这些成员上撤销，同时不动任何照片自己的手动覆盖——而当被撤销的照片*仍然*属于另一个自身声明了方案的相册时，它会改为被落上那个相册的方案，而不是留成未评分状态（这种重新推导仅限于正在被移出相册的那些具体照片；删除或清空整个相册不会尝试这么做）。`GET /api/albums/{id}/suggested_context` 会根据相册中占主导地位的已检测 `narrative_moment`（依据每个方案的 `suggest_from_moments` 列表）给出建议，并附带一个 `share` 置信度——它什么都不写；上面的指派仍然需要显式确认。要让新的方案真正改变任何照片已存储的类别，还需要执行一次重新计算（`POST /api/scan/recompute`）。

### 作品集导出

当 `viewer.features.show_portfolio_export` 为 `true`（默认）且编辑模式已解锁时，每张手动相册卡片都会增加一个**导出作品集**操作。它会打开一个小对话框（照片库标题、目标文件夹、是否包含照片描述），把相册渲染成一个自包含的静态 HTML 相册——即 thumbsup/sigal 那类用途，但是原生实现，不依赖任何外部工具。输出目录中包含 `index.html`（一个纯 CSS 的响应式缩略图网格，内置原生 JS 灯箱——**零**外部/CDN 引用，因此完全离线可用）、一个存放按序命名 JPEG 的 `assets/` 文件夹（不泄露照片库路径），以及一个记录数量和每张照片来源的 `manifest.json`。每张照片优先使用磁盘上的**原图**（缩放到 `portfolio.max_edge`，并应用 EXIF 方向），当原图不可达时（离线的网络共享）回退到已存储的 640px 缩略图。端点是 `POST /api/albums/{album_id}/export-portfolio`（受编辑模式限制）；`target_dir` 会按与复制／移动导出端点相同的白名单（`viewer.export.allowed_target_dirs` 加上扫描目录，参见[配置——导出与选片目标目录](CONFIGURATION.md#导出与选片目标位置)）进行校验，超过 `portfolio.max_photos`（默认 500）的相册会被拒绝。重复导出同一个相册是幂等的——只有本次导出自身的文件会被重写。参见[作品集导出配置](CONFIGURATION.md#作品集导出)。

API：参见下文的 [API 端点](#api-端点)一节。

由 `viewer.features.show_albums` 控制（默认：`true`）。

### 客户选片

客户的选片与你的照片库完全隔离。它们存放在专用的 `album_client_picks` 表中，被限定在该相册的照片范围内，绝不会触碰你自己的收藏／评分（`photos.is_favorite` / `user_preferences`），也不会训练个人排序模型。作为所有者，你可以从相册卡片上的 `[Edition]` 对话框读取这些选片。会话是短期的（`viewer.proofing.session_minutes`，默认 24 小时），并在相册取消分享或客户选片被禁用的那一刻立即失效。

## AI 点评

把一张照片的各项评分拆解为优点、不足和改进建议。

### 基于规则的点评

所有 VRAM 配置档都可用。分析已存储的指标（美观度、构图、清晰度、人脸画质等），生成对该评分的结构化解释。

拆解结果还会呈现可解释的**形式与色彩和谐**行（对称性、平衡感、边缘方向熵、分形复杂度、松田色彩和谐度——由 `--recompute-form` 填充）、针对可能存在缺陷的**畸变属性标签**（运动模糊、偏色、过度锐化……——来自 `--recompute-distortions`），以及针对肤色色度偏离自然值的人像给出的**肤色提示**（`--recompute-skin-tone`）。三者都只是参考——它们解释照片，并不改变综合评分——且每一行只在对应的数据列已填充时才显示。

### VLM 点评 `[GPU]` `[16gb/24gb]`

使用已配置的 VLM（Qwen3.5-2B 或 Qwen3.5-4B）给出结合上下文的点评。需要 16gb 或 24gb VRAM 配置档，以及 `viewer.features.show_vlm_critique: true`。

提示词是一条可配置的阶梯（`critique.vlm`），会注入完整的规则拆解、扣分项和 EXIF，回复按**观察 / 评价 / 建议**呈现。结果按照片缓存（`photos.vlm_critique`）并按需翻译，另有**重新生成**按钮可重新计算。它基于已存储的缩略图运行，因此 RAW 文件也能正确点评，而不会悄无声息地失败。

API：参见下文的 [API 端点](#api-端点)一节。

由 `viewer.features.show_critique`（默认：`true`）和 `viewer.features.show_vlm_critique`（默认：`true`）控制。

**“为什么是这个评分”可视化叠加层。**当 `viewer.features.show_saliency_overlay` 为 `true`（默认）时，点评对话框会增加一个**显示叠加层**开关：它会把 BiRefNet 显著性图以半透明热力图的形式绘制在照片之上（按需从已存储的缩略图重新计算——`GET /api/saliency_overlay`），再加上由已存储的关键点重建出的柔和人脸框和眼睛标记（`GET /api/photo/face_markers`）。睁眼时框为绿色，闭眼时为琥珀色。热力图只是示意（缩略图分辨率），并非像素级精确；在无法生成显著性掩膜的配置档上，该开关会自行隐藏。

## AI 照片描述 `[GPU]` `[16gb/24gb]` `[Edition]`

为任意照片获取 AI 生成的自然语言描述。描述在首次请求时生成，并缓存在数据库的 `caption` 列中。在编辑模式下可以通过照片详情页手动修改描述。（描述的*翻译*在 CPU 上运行——见下文。）

API：参见下文的 [API 端点](#api-端点)一节。

也可通过 CLI 批量生成和翻译：

```bash
python facet.py --generate-captions      # 为所有尚无描述的照片生成描述
python facet.py --translate-captions     # 把描述翻译成所配置的目标语言
```

描述翻译使用 MarianMT（CPU，无需 GPU）。在 `scoring_config.json` 的 `translation.target_language` 下配置目标语言（默认：`"fr"`）。支持的语言：法语、德语、西班牙语、意大利语。

由 `viewer.features.show_captions` 控制（默认：`true`）。基于 VLM 的照片描述需要 16gb 或 24gb VRAM 配置档。

## 常见工作流

- **筛选一次假期的照片**——打开“照片胶囊”→ 找出该行程日期自动生成的 `journey` 胶囊。每个胶囊都提供“保存为相册”操作。

## 照片胶囊

按主题、地点、人物和时间分组的精选照片幻灯片——点击一个胶囊即可播放。通过 `/capsules` 路由访问。

### 胶囊类型

胶囊会用多种算法从你的照片库中自动生成：

- **Journey（旅程）**——通过 GPS 聚类检测出的行程，附带反向地理编码得到的目的地名称（“罗马之旅 —— 2025 年 3 月”）
- **Moments with [Person]（与某人的时光）**——每位已识别人物的最佳照片
- **Seasonal Palette（季节色板）**——按季节 + 年份分组的照片
- **Golden Collection（黄金收藏）**——综合评分前 1%
- **Color Story（色彩故事）**——通过 CLIP 嵌入向量聚类得到的视觉相似分组
- **This Week, Years Ago（往年本周）**——把“那年今日”扩展到 ±3 天
- **Location（地点）**——带地理标记的照片聚类，附地名
- **Favorites（收藏）**——按年份和季节分组的收藏照片
- **Dimension-based（按维度）**——依据相机、镜头、类别、构图模式、焦段、拍摄时段、星级评分以及跨维度组合自动生成

### 幻灯片播放

点击任意胶囊卡片即可开始幻灯片播放。功能包括：
- **主题化转场**——滑动（旅程）、缩放（人像）、肯·伯恩斯效果（黄金收藏／季节）、交叉淡入淡出（默认）
- **自动接续**——一个胶囊播放结束时，会先显示一张过渡卡片介绍下一个胶囊，然后继续播放
- **随机播放与续播**——照片会被打乱以增加变化；每个胶囊的播放位置会被单独记录
- **自适应分组**——竖幅照片会根据视口宽高比并排分组
- **保存为相册**——把任意胶囊保存为永久相册

### 时效性

胶囊按可配置的周期轮换（默认：24 小时）。封面照片和带种子的发现类胶囊与同一个轮换周期对齐。顶栏的“重新生成”按钮可强制立即刷新。

### 反向地理编码

地点类和旅程类胶囊会显示地名（例如“法国，巴黎”）而不是坐标。它使用 `reverse_geocoder` 包做离线地理编码——无需任何 API 调用。结果会缓存在数据库中。

安装：`pip install reverse_geocoder`

API：参见下文的 [API 端点](#api-端点)一节。

所有设置项参见[配置——照片胶囊](CONFIGURATION.md#照片胶囊)。

## 导出到后期软件

把你的星级、收藏和淘汰标记以 XMP 附属文件的形式写入磁盘，让外部后期软件（darktable、Lightroom）能够读取。需要编辑模式。

- **从照片库**——选中照片，然后 **操作 → 导出** 会在每个文件旁写入一个附属文件。导出整个筛选后的视图（而非手工挑选的照片集）上限为 10 000 张：更大的视图会被直接拒绝，提示信息会给出该视图的照片数量和上限，且不写入任何内容。它绝不会被截断——把你以为是完整的选择只导出了一半，比一次明确的拒绝更糟糕——因此请缩小筛选范围后重新导出。
- **从相册**（“选片篮”）——把整个相册导出为附属文件，或把文件复制／符号链接到目标目录（与[选片后导出／清理](#选片后导出清理)使用同一份目标目录白名单）。
- **把元数据写入文件**——照片详情中的“把元数据写入文件”操作会在写入附属文件之外，把星级／关键词直接嵌入原始文件（JPEG/HEIC/TIFF/PNG/DNG，通过 exiftool），这样整个照片生态都能看到它们。专有 RAW 原始文件永远不会被修改。由 `viewer.features.show_embed_metadata` 控制（默认：`true`）。

## 选片

选片页面（`/culling`，编辑模式）会把几乎相同的镜头分组，方便你从每组中留下最好的、淘汰其余的。工具栏中第一个、也是影响最大的控件——**粒度**选择器——决定照片如何分组：

- **全部**（默认）——把连拍分组和相似分组合并在一起。
- **连拍**——拍摄时间相近的照片（来自连拍检测）。
- **相似**——不论何时拍摄、看起来相像的照片，按 CLIP/SigLIP 嵌入向量相似度分组。阈值滑块控制分组的严格程度。
- **场景**——按时间顺序的场景分组（拍摄时间上的连续段），每组标题给出其时间跨度和占主导的叙事时刻。受 `viewer.features.show_scenes` 控制。
- **包围曝光**——由 [`--detect-sequences`](COMMANDS.md) 找出的多曝光照片组，基准曝光排在最前，每一帧都标注其曝光补偿（`-2 EV` … `+2 EV`）。它被有意排除在**全部**之外：一组包围曝光是同一个主体拍了多次以便合成，而不是一组互相竞争的照片，因此每一帧一开始都被标为保留，确认时不记录任何比较对——在一组曝光阶梯中偏好某一档说明不了你的审美。若想去掉两侧的曝光帧，请使用下文自动选片的包围曝光修剪功能。
- **全景**——由 [`--detect-panoramas`](COMMANDS.md) 找出的待拼接扫拍照片组，按拍摄顺序排列，中间帧被标记为该组的代表。与包围曝光完全一样整组保留：每一帧一开始都被标为保留，确认时不记录任何比较对。
- **HDR 全景**——同一次检测过程识别出的高动态范围扫拍（曝光跨度超过 `hdr_min_span_stops`），同样整组分组并整组保留。没有单独的“HDR 包围曝光”粒度：三脚架 HDR 组在每个位置上都做了包围曝光，因此包围曝光检测会先把它标为普通的**包围曝光**，只有当全景检测识别出这是一次扫拍之后，该标签才会被 `hdr_panorama` 取代。全景检测没能识别出的三脚架 HDR 组也不会丢失——它只是继续留在**包围曝光**之下。

这三种粒度（**包围曝光**、**全景**、**HDR 全景**）属于“整组保留”类型：在别处用来快速“只保留这一张”的双击手势在这里是空操作——一组包围曝光或一次扫拍是为了合成而拍的，不是为了互相竞争，因此暗房拒绝把它们缩减为单独一帧。它们的列表也完全忽略照片库的 `hide_*` 开关，与照片网格（默认只显示一组的代表帧）恰恰相反：无论照片库被配置为隐藏什么，每一组尚未复核的照片在这里都会逐帧完整显示。与连拍／相似／场景分组一样，在排除掉已被淘汰的成员之后剩余不足 2 帧的一组，会被从列表中剔除而不是显示成只有一张照片的分组。

粒度旁边还有两个排序控件：**排序模式**（最容易的优先、最冗余的优先、最好的优先、最新的优先、最需要比较的优先，或**最早的优先**）以及一个**把当前模式反向排列的箭头按钮**。“最早的优先”是唯一一种同时把每一组*内部*的照片也按拍摄顺序排列的模式，而这也是包围曝光或一次摇摄序列唯一读得通的顺序。

对每一组挑出要保留的照片；确认后其余照片被淘汰。确认是延迟提交的，可以撤销（参见[撤销](#撤销)）。粒度、排序和类别的选择会保存在 `localStorage` 中。不适用于当前粒度的控件会被隐藏——场景模式下排序下拉框和相似度阈值滑块会消失，而在你没有任何手动相册时作用域按钮会被隐藏。每个工具栏按钮和分组操作按钮都带有提示文字，小屏幕上工具栏会脱离出来变成可滚动的底栏。

**限定作用域的选片。**暗房可以通过查询参数收窄到一个子集：`?group_by=scene` 切换到场景粒度，`?album=<id>` 限定在某个相册内，`?from=&to=`（EXIF 拍摄时间窗口，也是**筛选此场景**的基础）限定在一个场景内。横幅会显示当前生效的作用域，并带有**退出场景**控件；连拍成员的获取仍限定在相册内，但忽略时间窗口，因此跨越场景边界的连拍仍会显示它的全部帧。

**“我的偏好”标签。**每一次确认都会记录 `source='culling'` 的比较行来训练个人排序模型，因此顶栏会显示一个“我的偏好 · N 次对比”的小标签，并在每次决定后更新——你在选片的同时 AI 也在学习你的眼光（`GET /api/ranker/status`）。

**题材预设。**工具栏中的**预设**选择器会一次性套用一整套针对某类题材的选片参数——严格程度、保留配额、相似度阈值以及暗房的闭眼／表情欠佳人脸阈值——因此体育题材只保留一组连拍中最锐利的一张，婚礼题材保留更多睁眼的版本，演唱会和野生动物题材则放宽人脸相关的限制。选择会保存在 `localStorage` 中；手工调整任何一个参数都会把标签变回“自定义”。预设定义在 [`cull_profiles`](CONFIGURATION.md#按题材区分的选片配置) 配置块中（`GET /api/culling/profiles`）。

### 自动选片

工具栏中的**自动选片**按钮可以一次处理整个作用域，而不必逐组处理。用粒度／作用域控件选定范围（全部分组，或仅连拍／相似／场景，可再限定相册或日期窗口），设置**严格程度**——也就是保留配额，越高每组保留得越少——然后预览。每一组会保留最佳的那张照片，外加严格程度容差范围内的所有照片（并设有每组的下限），其余被淘汰。在三种整组保留的粒度（**包围曝光**、**全景**、**HDR 全景**）下该按钮会被完全隐藏——那里没有什么需要它决定，因为那些组的每一帧一开始就都是保留状态。在混合作用域中，包围曝光会先于连拍、相似和场景被决定，因此包围曝光的基准曝光帧绝不会被它恰好也属于的后续分组重新决定。

预览是一次**试运行**（不写入任何内容）：它显示每组的保留／淘汰划分。确认后即应用——淘汰会被记录下来，并像每一次选片一样训练“我的偏好”；可选的**精华**相册会以幂等方式收集每组中评分不低于 `auto_cull.highlights_min` 的最佳照片。当自动选片会保留与当前代表帧不同的一帧时，该组会被打上“本组中有更好的照片”提示徽章。端点为 `POST /api/culling/auto`；通过 [`auto_cull`](CONFIGURATION.md#自动选片) 配置块设置。

当已训练出保留照片排序头时，`POST /api/culling/auto` 会在其通过准确率门槛后按 `keeper_prob` 挑选每组要保留的照片——否则输出与启发式挑选逐字节一致。

**修剪多余的包围曝光**需要主动开启（`trim_brackets`，默认关闭），而且这是自动选片中唯一会缩减序列照片组的路径——在其他任何地方，混合作用域碰到的包围曝光、全景或 HDR 全景都会整组保留，不受严格程度影响。一组包围曝光之所以值得多拍几帧，是因为它覆盖了基准曝光会裁掉的动态范围；当基准帧既没有暗部裁切也没有高光裁切时，就没有什么需要挽回的，于是两侧的曝光帧只是占用存储而不是提供宽容度——也就是“我一直开着包围曝光”这种情况。只有基准帧会被保留，判定依据是哪一帧是基准曝光，而绝不是评分或严格程度；基准帧从未被测量过的照片组则不会被动——未测量与未裁切并不是一回事。

### 全屏

按 **`F`**（或顶栏开关）可调用浏览器全屏 API 进行满屏复核——暗房会填满屏幕，不显示任何应用外框。该按键列在暗房的快捷键说明中；按 `F` 或 `Esc` 退出。

### 放大镜与 Z 键缩放

在单张视图的灯箱中按 **`Z`** 可切换 Photo Mechanic 式的放大镜（适配 ↔ 2×；滚轮／`+`／`-` 最高可缩放到 800%）。超过适配比例后，该窗格会把缩略图换成全分辨率的 `/image` 源，因此你无需离开视图就能在真实像素上判断合焦是否精准。在“场景”的接触印相条上，`Z` 会切换一个跟随光标在图块上移动的悬停放大镜（取自全分辨率图片），并配有可调的缩放滑块。已存储的缩略图上限为 640px，因此要看得比这更细就得靠放大镜。

### 每张人脸的标记

在连拍／相似选片灯箱中，每一张被检测到的人脸都带有自己的标记——睁眼／闭眼、表情欠佳以及检测置信度——而不是整张照片只有一个闭眼标志。这让合影更容易筛选：一眼就能看出哪张脸闭了眼或表情不佳。这些标记会通过一次批量调用（`POST /api/culling-group/faces`）为整组一次性获取。

暗房的**人脸面板**会根据连续的睁眼分数和微笑分数把每个人脸裁切图标为绿／橙／红，并新增了实时的**眼睛**和**微笑**阈值滑块，让你随时调整什么算闭眼、什么算表情欠佳。这两个界限对应配置键 `face_detection.eyes_closed_max` 和 `face_detection.poor_expression_min`（默认均为 `4.0`）；滑块的初始值就取自它们。

**主体特写条（无人脸分组）。**对于照片中没有显著人脸的连拍／相似分组——野生动物、微距、产品、鸟类——暗房会改为显示一条**主体**条：把每一帧的关键主体按已保存的 BiRefNet 主体框裁切出来并排列在一起，让你在特写下比较真正的主体（即 Zoner 的“AI 特写”思路，这里是原生实现）。每个裁切图都带有一个按组归一化的清晰度徽章（10 = 该组中最清晰的主体）和一个彩色圆环（绿／琥珀／红），让那张真正锐利的帧脱颖而出；点击某个裁切图会把主视图跳转到那张照片。这些裁切图直接从已存储的缩略图上切出，不运行任何模型（`POST /api/culling-group/subjects`），并且只在一组照片有主体但没有人脸时出现。它只有在照片带有主体框之后才会启用：对已有照片库运行 `python facet.py --recompute-saliency`（GPU）进行回填——在那之前该条目根本不会出现。

**关键主体（缩放目标 + 关键人物）。**暗房会判断当前打开的这组照片中每一帧究竟是关于谁或关于什么的——是检测到的人脸中最好的那张，没有人脸时则是已保存的 BiRefNet 主体框——整组只需一次调用（`POST /api/photos/key_subjects`），然后*对着*它缩放：**`Z`**、双击，或离开适配比例的第一次滚轮操作，都会把 1:1 视图落在那个点上，而不是画面正中，因此一次像素级细看是从真正重要的那张脸开始的。一旦你自己平移或滚轮操作过某一帧，这个建议就会对该帧退让——它绝不会重新框住你选定的取景。当胜出者是一位具名人物时，该人脸会在人脸条中带一个琥珀色的名字标签。人脸优先于显著性，而在人脸之间，相对大小、居中程度和是否具名人物的最佳组合胜出，因此中景里的一位具名人物会胜过更大的陌生人，而背景里一个具名的小点则不会。这些结果不会被存储，因此答案始终反映当前的人脸和人物指派；框的坐标是相对于完整画面的比例（`normalized_frame_xyxy`），而不是相对于屏幕上的缩略图。`GET /api/photo/key_subject` 为单张照片提供同样的答案。

**同步比较（2 联 / 4 联）。**灯箱顶栏有“单张 / 比较 2 张 / 比较 4 张”按钮。在比较模式下各窗格共享同一个平移／缩放变换，因此在任一窗格上滚轮缩放或拖拽平移都会让所有窗格移动到完全相同的裁切位置——这才是靠真正看像素来挑出一组连拍中最锐利那帧的方法。双击可在适配 ↔ 缩放之间切换；超过适配比例后每个窗格会惰性地把 1920px 缩略图换成全分辨率的 `/image` 源，让细看足够清晰。无需后端改动——两条图片路由都已存在。（触摸捏合尚未接入；桌面端请用滚轮。）

**滑动保留或淘汰（触摸）。**在触摸设备上，暗房的单张视图同时也是一副滑动卡组：把画面向右拖是保留，向左拖是淘汰，拖动过程中它会倾斜并染色——绿色配 KEEP 徽章，红色配 REJECT 徽章。超过画面宽度的 35%（且不少于 48px）后松手，卡片就会朝那一侧飞出，写入与 `↑` / `↓` 键完全相同的决定，并像 `→` 一样跳到下一帧；不到这个距离则回弹，什么也不决定。一旦判定某次拖动的轴向是垂直方向，它会被立即原样释放，因此归属不变。每次提交都会弹出带**撤销**的提示条，它恢复的既是那个决定*也是*做出决定的那一帧——按错 `↑` 可以用 `↓` 撤回，但手指滑错时你已经在下一帧上，没有相反的手势可用。这个手势只在不会与别的手势冲突的场合才提供：粗指针（手指或触控笔，绝不是鼠标）、单张视图（比较网格中没有哪一帧是滑动的对象）以及适配比例——超过之后，同样的拖动*就是*该窗格的平移，而窗格已经捕获了指针。第一帧下方会有一行提示，直到你关闭它为止（记录在 `localStorage` 中）。

**修图效果预览。**在单张视图中，暗房顶栏会增加一个**调色板**菜单，列出“原图”以及每一个已配置的 darktable 样式，让你能基于*已冲洗*的效果而不是平淡的 RAW 预览来选片——这才是按照片最终交付的样子来判断它的方式。选定一个样式会通过 darktable-cli 渲染原图（`--style`，受 `preview_max_edge` 限制）并替换到主图上，渲染时显示加载动画，失败时给出提示条并退回原图。所选样式在当前分组的各帧之间保持不变，重新打开暗房时重置（仅限本次会话，绝不保存）。只有在至少配置了一个样式**并且** darktable-cli 可用时该控件才会出现；这些样式必须已经存在于运行查看器那位用户的 darktable 配置中。渲染出的预览会缓存在磁盘上（以源文件 mtime、样式和最大边长为键），因此再次查看某一帧是瞬时的。端点：`GET /api/photo/cull_preview?path=&style=`（受编辑模式限制）；通过 [`raw_processor.darktable.cull_styles`](CONFIGURATION.md#raw-解码) 配置。

API：参见下文的 [API 端点](#api-端点)一节。

## 场景视图

以**只读**方式浏览按时间顺序分成“场景”的照片库——按拍摄时间上的连续段以故事顺序展示，带网格、悬停放大镜以及日期／时刻标题。对**所有已通过身份验证的用户**开放（只读用户和编辑用户皆可）。照片按拍摄时间的间隔切分成场景（相邻两张之间间隔超过 `scenes.gap_minutes` 时开启新场景，在拍摄稀疏时会自适应放宽），过长的连续段还会被再切分，这样一场连续拍摄的活动不会塌缩成一个巨大的场景。

唯一的入口是相册网格中每个相册的**显示此相册的场景**操作按钮（浏览界面内还有一个相册作用域选择器可切换范围）。主导航中没有“场景”入口。每个场景都带有一个仅编辑模式可见的**筛选此场景**按钮，可深链到场景粒度下的[选片](#选片)界面（`/culling?group_by=scene&album=&from=&to=`）；编辑用户也可以直接从“选片”导航进入场景形式的选片。浏览界面本身没有淘汰网格和批量确认——所有选片现在都通过统一的选片界面完成。

当叙事时刻已经计算出来（见下文）时，每个场景还会以其占主导的时刻命名，而 `scenes.split_on_moment_change` 可以在时刻发生变化的地方把长连续段再切分开。

## 叙事时刻

Facet 会为每张照片标注它所描绘的场景／活动“时刻”。默认的 **general** 词表与照片库内容无关——庆祝、用餐、海滩、水上活动、山地、自然与野生动物、城市景观、旅行地标、演唱会、体育、聚会、人像、儿童、宠物、夜生活、典礼、风光、冰雪与冬季、居家室内、道路与车辆——或者 `other`（另有一个 `wedding` 词表作为可选题材提供）。Narrative Select 和 AfterShoot 都不做这件事；它们只按时间和视觉相似度分组。

它是**零样本且完全本地**的，并且是**基于描述语义**的：每张照片的 AI 描述会被编码一次并存储下来，时刻就是该描述嵌入向量与每个时刻的文本提示之间取**最大池化**余弦相似度后的最佳者（L0）——照片没有描述时，回退到已存储的图像嵌入向量。描述信号匹配时刻的清晰程度约为原始图像的 2.4 倍。小幅的人脸／标签先验用于打破接近的平局（L1），随后一个 Viterbi 过程会**沿时间线做平滑**，把孤立的误判拉回到周围的连续段中（L2）。可选的 VLM 决胜环节（L3，16gb/24gb）可以重新判定低置信度的帧。描述嵌入向量只计算一次并可重复使用，因此重新标注只是对已存储向量做一次廉价的点积——无需解码图像，也无需逐张跑模型；它会在**每次扫描结束时自动运行**（只对新增的描述做编码）。对已有照片库的第一次完整处理会编码所有描述（建议使用 GPU）；用 `python facet.py --recompute-moments` 可重新标注整个照片库。

时刻会以场景标题的形式呈现，也可作为照片库的筛选条件（`GET /api/photos?narrative_moment=beach`，选项来自 `GET /api/filter_options/narrative_moments`）。词表按活动类型由配置驱动——调整提示词／阈值或切换题材请参见[配置——叙事时刻](CONFIGURATION.md#叙事时刻)。

**时刻置信度。**每个标签都会存储一个后验置信度（`narrative_moment_confidence`）。低于 `viewer.moment_confidence_min`（默认 `0` = 从不变暗）的标签，会在“场景”标题、选片的场景分组标题以及照片库的照片提示信息（同时还会显示置信度百分比）中以变暗并带“（不确定）”后缀的方式呈现。置信度同时也是一个排序选项——“内容”分组下的**时刻分组置信度**（NULL 值排在最后）——以及一个照片库区间筛选条件（`min_moment_confidence` / `max_moment_confidence`，侧边栏**拍摄时刻**分区中的 0–1 滑块）。

- 每个场景按拍摄顺序显示它的代表照片
- 用场景的**筛选此场景**按钮筛选它，该按钮会打开限定于该场景的选片界面
- 小于 `scenes.min_size` 的场景会被略过；最多加载 `scenes.max_photos` 张照片

API：参见下文的 [API 端点](#api-端点)一节。

由 `viewer.features.show_scenes` 控制（默认：`true`）。`gap_minutes`、`min_size`、`max_photos`、`max_scene_size`、`adaptive` 和 `adaptive_k` 参见[配置——场景](CONFIGURATION.md#场景)。

## 废片清理

针对业余照片库中堆积起来的非摄影“废片”——截图、扫描文档、收据、表情包和演示幻灯片——提供的快速复核队列。检测基于已存储的图像嵌入向量以零样本方式进行（参见[配置——废片清理](CONFIGURATION.md#废片清理)）；运行 `python facet.py --detect-junk`（或让它在每次扫描结束时自动运行）来填充 `junk_kind`。

从**废片清理**导航按钮打开它（`/junk` 路由，仅编辑模式）。该页面复用照片库网格，显示每一个被标记的候选项：

- **类型筛选标签**——“所有类型”外加每个已检测类型及其数量的标签（来自 `GET /api/filter_options/junk_kinds`）。点击可把队列收窄到某一类型。
- **保留**（逐张）——清除废片标签，让该照片**永久**离开队列：它会被标记为已评估且干净（`not_junk`），之后的 `--detect-junk` 不会再次标记它。
- **淘汰**（逐张）——用与别处相同的淘汰机制把照片标为淘汰（不会从磁盘删除任何内容）。
- **淘汰当前显示的全部照片**——批量淘汰当前已加载的所有候选项，需经确认对话框。
- **放大镜**——按 **`Z`**（或工具栏开关）启用 Photo Mechanic 式的悬停放大镜，方便在做决定前看清细小文字。

废片照片**不会**从普通照片库中隐藏——在你专门筛选它们之前，它们一直可见。用 `?junk_kind=<kind>`（精确匹配）或 `?junk_kind=any`（任意废片，排除 `not_junk` 哨兵值）可筛选任意照片库视图。

由 `viewer.features.show_junk_sweep` 控制（默认：`true`）。

### 类别优先级与拍摄场景评分方案

类别按 `priority` 升序求值，第一个匹配的筛选条件胜出——完整模型参见[筛选条件求值](SCORING.md#评分的工作原理)和[拍摄场景评分方案](CONFIGURATION.md#拍摄场景评分方案)。有两个受编辑模式限制的调节手段可以管理它，而无需手工编辑 `scoring_config.json`：

- **全局优先级**——`GET/POST /api/config/category_priorities` 列出并重排基础求值顺序。`POST` 接受一个完整有序的类别名称列表，并把现有的优先级数值按该顺序做置换，因此这些数值的多重集（及其唯一性）得以保留，而不是重新编号。
- **拍摄场景评分方案**——`GET /api/config/scoring_contexts` 列出已配置的预设（`default`、`action_stage`、`party_event`、`portrait_session`、`wildlife`、`landscape`、`motorsport`）以及每个预设解析后的实际生效顺序。一个方案会把某些类别提到最前面，并把另一些完全排除在外，而不触动全局顺序。每个非 `default` 预设的 `promote`／`excluded` 增量本身都可以在同一个**拍摄场景评分方案**标签页中编辑——拖拽调整被提前类别的顺序（或使用上移／下移按钮）、切换某个类别的排除状态、保存——通过 `PUT /api/config/scoring_contexts/{name}`（受编辑模式限制，请求体 `{promote, excluded}`）；它会拒绝未知类别、两个列表中出现的 `default` 以及 `promote` 内部的重复项，而同时出现在两个列表中的名称会被接受，并以 `excluded` 为准。`label_key` 和 `suggest_from_moments` 不能在这里编辑。方案可以按相册指派（参见“相册”下的[拍摄场景评分方案](#拍摄场景评分方案)），也可以通过下文的类别覆盖按单张照片指派。

这两个调节手段本身都不会重新为照片评分。在重排优先级、指派方案或设置单张照片的覆盖之后，请触发一次重新计算（`POST /api/scan/recompute`，受编辑模式限制），并轮询 `GET /api/scan/recompute_status` 获取 `{running, kind, progress, exit_code}`。`/scan/start` 和 `/scan/recompute` 都由 `facet.LibraryLock` 做跨进程保护，而不仅仅是查看器内存中的作业锁（参见[重排全局优先级](CONFIGURATION.md#调整全局优先级顺序)）：若已有从终端启动的重新计算或扫描在运行，查看器会以 409 拒绝新作业并指出持有者，因此 CLI 作业与查看器触发的作业不会再撞车。如果启用了 `normalization.per_category`，那么在影响类别的改动之后仅做一次重新计算并不会完全收敛——参见[归一化](CONFIGURATION.md#归一化)。

同一标签页中的**类别冲突**面板（`GET /api/stats/categories/overlap`）的存在，就是为了在任何重排之前回答：哪个更高优先级的类别正在悄悄抢走某个类别的照片，抢走了多少。它的表格按类别列出：当前有多少张照片被指派给它（**已指派**）、若单独求值该类别的筛选条件时照片库中有多少张会匹配（**匹配筛选条件**），以及其中有多少被更高优先级的类别抢走（**被更高优先级抢走**，即 `matched - assigned`，下限为 0）。下方的**最常冲突的类别对**列表按共有照片数量排出最常被同时匹配的类别组合。被固定的 `default` 兜底类别在表格和类别对列表中都被排除——它按设计会匹配每一张照片（筛选条件集为空），把它算进来会淹没所有真正的冲突。

### 类别覆盖

要从比较视图重新指派一张照片的类别：编辑类别徽章，选择目标类别，运行“分析筛选条件冲突”查看哪些筛选条件把它排除在外，然后应用覆盖。该覆盖会针对已配置的类别名称进行校验（`POST /api/comparison/override_category`），并且现在会持久化到 `photo_scoring_overrides` 侧表中——与以前不同，它能挺过下一次重新计算而不是被悄悄丢弃，照片会一直保持被手动指派的类别，直到它被显式清除（`POST /api/comparison/clear_category_override`）。

同样这两个操作在照片灯箱中也可以使用，位于**设置评分类别…** / **清除覆盖**之下（受编辑模式限制），旁边还有一个可折叠的**为什么这不是另一个类别？**面板。在那里选定一个目标类别，面板就会报告当前是哪些筛选条件把这张照片排除在外，以及每一条各需要变成什么——例如*“把 shutter_speed_max 从 0.02 提高到 0.033”*。这是弄清某个类别对某张照片而言是根本不可达、而不只是排名靠后（后者仅靠重排是解决不了的）最快的方式。它由 `POST /api/comparison/suggest_filters` 支撑。

## 数码相框与展示屏端点

无需登录的展示设备——智能相框、Home Assistant 仪表盘、ImmichFrame / Immich-Kiosk 一类的显示屏——无需用户会话就能拉取 Facet 的最佳照片。这里**没有客户端界面**：展示设备直接调用这些端点，通过 `frame` 配置块中配置的长效不透明**相框令牌**（`frame.tokens`，空列表会禁用整个功能，所有端点返回 404）进行认证。令牌以 UTF-8 字节做常量时间比较，因此缺少令牌是 401，令牌错误或含非 ASCII 字符是 403——绝不会是 500。

内容策展取自整个照片库：已淘汰、废片和闭眼照片会被排除，`frame.min_aggregate`（默认 7.0）设定评分下限，可选的 `frame.favorites_only` / `frame.categories` 可进一步收窄范围。照片通过**按评分加权的随机采样**返回（对按评分排出的候选池做一次打乱），因此相框展示的是你最佳照片中的多样内容，而不是每次都那么几张。响应**绝不包含文件系统路径**——每张照片都用一个不透明的签名 id 寻址（用服务器密钥对该行的 `rowid` 签名），因此持有令牌的一方无法枚举任意行，也无法得知你的文件放在哪里。

| 端点 | 返回 | 缓存 |
|----------|---------|-------|
| `GET /api/frame/photos?token=&count=` | `{photos: [{id, caption?, date_taken?, width, height}]}`——`count` 的上限为 `frame.max_count`（默认 100），默认值取 `frame.count`（20） | — |
| `GET /api/frame/image/{id}?token=&max_edge=` | 该照片的 JPEG——磁盘上的原图缩放到 `max_edge`（受 `frame.max_edge` 限制，默认 1920），原图不可达时回退到已存储的缩略图 | 长期不可变 |
| `GET /api/frame/next?token=` | 一张随机的精选 JPEG，每次调用都不同——适用于简易相框／Home Assistant 通用摄像头场景 | `no-store` |

### 生成令牌

令牌是由你自己想出来的不透明字符串——请使用足够长的随机串，并像对待密码一样对待它：

```bash
python -c "import secrets; print(secrets.token_urlsafe(32))"
```

把结果加入 `scoring_config.json` 中的 `frame.tokens`（可以列出多个——每台设备一个——删除某一个即可吊销它）：

```json
"frame": {
  "tokens": ["Xu8w…your-random-token…"],
  "count": 20,
  "min_aggregate": 7.0,
  "max_edge": 1920,
  "favorites_only": false,
  "categories": []
}
```

### Home Assistant 配置示例

单一 URL 的 `/api/frame/next` 可以直接对应到 Home Assistant 的[通用摄像头](https://www.home-assistant.io/integrations/generic/)——每次刷新都会拉取一张新的精选照片：

```yaml
camera:
  - platform: generic
    name: Facet Frame
    still_image_url: "http://facet.local:5000/api/frame/next?token=Xu8w…your-random-token…"
    verify_ssl: false
    framerate: 0.05  # 大约每 20 秒刷新一次
```

把这个摄像头加入 Picture Glance / Picture Entity 卡片（或墙面平板的仪表盘），它就变成了一个会自动更新的数码相框。

对于自行管理幻灯片播放的 **ImmichFrame 式**消费端，请轮询 `GET /api/frame/photos?token=…&count=30` 获取 id 列表，然后逐个请求 `GET /api/frame/image/{id}?token=…&max_edge=1920`——这些 id 是稳定的，且图片响应带有长期不可变缓存，因此客户端只需获取每张照片一次，就可以自行在它们之间做交叉淡入淡出。

## 手机自动上传

`/dav` 下有一个极简的 **WebDAV** 端点，可让手机自动上传应用（PhotoSync，以及任何支持 WebDAV 的客户端）把照片直接推送到 Facet 的**收件目录**。把收件目录指向你的某个扫描目录（或其子目录），并对它运行 `facet.py --watch`：每张上传的照片一落地就会被自动评分——即 PhotoPrism 的移动端同步模式。

这是**只负责上传的管道**——它绝不触碰用户会话或 JWT。访问采用 HTTP Basic 认证，使用 `upload` 配置块中配置的**共享设备凭据**（`upload.username` / `upload.password`），而**不是**用户账号。整个 `/dav` 树在禁用时返回 **404**：只有当 `upload.username`、`upload.password` 和 `upload.inbox_dir` 全部设置后该功能才会启用。每个操作都被限制在 `upload.inbox_dir` 内——路径穿越、绝对路径和符号链接逃逸都会被拒绝——上传以原子方式流式写入磁盘，大小上限为 `upload.max_file_mb`（默认 500）。

已实现的方法：`OPTIONS`、`PROPFIND`（深度 0/1）、`MKCOL`、`PUT`、`MOVE`、`DELETE`、`GET`、`HEAD`。`LOCK`／`UNLOCK` 未实现（上传客户端会把它们的缺失视为不加锁的共享）。

### 配置

```json
"upload": {
  "username": "phone",
  "password": "…a-long-random-shared-secret…",
  "inbox_dir": "/photos/inbox",
  "max_file_mb": 500
}
```

`inbox_dir` 应当位于某个被扫描的目录之下，这样 `--watch` 才能接住上传的文件：

```bash
python facet.py /photos --watch
```

### PhotoSync 配置示例

1. 在 PhotoSync 中添加一个 **WebDAV** 配置（Configure → Add Configuration → WebDAV）。
2. **URL / 服务器**：`http://<host>:5000/dav/`（填你的 Facet 主机；如果前面有反向代理则用 `https://`）。
3. **用户名 / 密码**：上面设置的 `upload.username` / `upload.password`。
4. **目标文件夹**：保持在根目录（`/`）即可放进收件目录，或使用 PhotoSync 通过 `MKCOL` 创建的子文件夹。
5. 在 Facet 主机上以监视模式扫描收件目录，这样上传的照片一到达就会被评分：

   ```bash
   python facet.py /photos --watch
   ```

### curl 冒烟测试

```bash
curl -T photo.jpg -u phone:'…a-long-random-shared-secret…' http://<host>:5000/dav/photo.jpg
```

返回 `201 Created`（覆盖时为 `204 No Content`）即表示上传已落到收件目录；`--watch` 会在下一次防抖后为它评分。

### 异步 SQLite（可选，用于高并发读取路径）

`api.database.get_async_db()` 是一个基于 aiosqlite 的异步上下文管理器，
与 `get_db()` 平行。目前各端点都是同步的（FastAPI 会把它们卸载到
工作线程池中，在通常的并发量下没有问题）。对于高并发
读取路径（同时超过 5 位用户），可以按以下方式逐个迁移
各端点：

1. 把 `def foo(...)` 改为 `async def foo(...)`。
2. 把 `with get_db() as conn:` 换成 `async with get_async_db() as conn:`。
3. 对每一个 `.execute()` 以及 `.fetchone()` / `.fetchall()` 加上 `await`。
4. 写入路径保持同步——aiosqlite 反正会把写入串行化，而同步
   路径的连接池已经能处理它们。

计划中最热的候选是 `/api/photos`、`/api/timeline`、
`/api/search`。请一次迁移一个，并在推广前做基准测试。

## API 端点

交互式 API 文档位于 `/api/docs`（Swagger UI），OpenAPI 模式位于 `/api/openapi.json`。

客户端的 TypeScript 类型由该模式通过 `cd client && npm run gen:api` 生成到 `client/src/app/core/api/schema.d.ts`。生成的文件会被提交进仓库，CI 会重新生成它并在出现差异时失败——因此响应模型与客户端读取它所用的类型不可能各自漂移。

### 照片库

| 端点 | 说明 |
|----------|-------------|
| `GET /api/photos` | 带筛选条件的分页照片列表 |
| `GET /api/photos/count` | `{ total }`——有多少照片符合当前照片库的筛选条件 |
| `GET /api/photos/paths` | `{ total, paths }`——所有匹配的路径，无序；仅由需要文件名的操作（下载、复制）按需使用，全选绝不会用到它。上限为 10000：超过此数的视图会被以 `412` 拒绝并给出数量和上限，而不是被截断——一份不完整的路径列表会让用户误以为选择是完整的——而且没有任何回退：该操作会带着一条“照片过多”的提示被放弃，让用户去缩小筛选范围后重试。只有真正需要字面路径列表的操作才会走这里；整个视图的选择本身只需计数（`GET /api/photos/count`），从来不需要路径列表，因此建立在其之上的、按筛选条件限定的操作（批量评分／淘汰写入、选片、附属文件导出）不受此上限影响，它们各有自己的上限 |
| `GET /api/photo` | 单张照片的详情 |
| `GET /api/photo/set?path=` | 一张照片所属的包围曝光／全景／HDR 全景／连拍／重复照片组（序列优先于连拍，连拍优先于重复），以 `path` 为键——绝不用分组 id，因为包围曝光和全景检测每次运行都会从 1 开始重新编号 |
| `GET /api/photo/histogram?path=&bins=` | 可直接绘制的亮度 + R/G/B 分箱数据（`bins` ∈ 32/64/128/256，默认 64），在扫描时对全分辨率图像测得。每个通道都按同一个全局最大值缩放，而不是各自的最大值。对于在引入分通道格式之前存储的行，`r`/`g`/`b` 为 `null`；当该行完全没有直方图时返回 404，这正是控件回退到对缩略图采样的信号 |
| `GET /api/type_counts?hide_blinks=&hide_bursts=&hide_duplicates=&hide_brackets=&hide_panoramas=` | 侧边栏类型标签所用的各类型照片数量。与照片库使用同样的五个开关；省略某个开关时会回退到 `viewer.defaults` 而不是“关闭”——要统计全部，请显式发送 `hide_bursts=0` 等 |
| `GET /api/similar_photos/{path}` | 相似照片（模式：`visual`、`color`、`person`） |
| `GET /api/search?q=&limit=&threshold=&scope=` | 语义化的以文搜图（`scope=text` = 仅 OCR／描述文本） |
| `GET /api/critique?path=&mode=&refresh=` | AI 点评（基于规则或 VLM）；`refresh=true` 会重新生成已缓存的 VLM 点评 |
| `GET /api/ranker/status` | “我的偏好”排序所用的个人排序模型状态（已学习覆盖率 %、留出集准确率） |
| `GET /api/config` | 查看器配置 |

### 批量操作

| 端点 | 说明 |
|----------|-------------|
| `POST /api/photos/batch_favorite` | 把多张照片标为收藏（并清除淘汰标记）。请求体必须恰好是 `{photo_paths}`（最多 1000）或 `{filters}` 之一——`filters` 接受与 `GET /api/photos` 相同的查询参数（均为字符串），且没有上限。`exclude`（可选，最多 1000）可与两者中的任意一个同时出现，用来收窄所发送的目标——从 `photo_paths` 中减去，或从 `filters` 范围中排除——因此它只能收窄，绝不会扩大。两个目标都不给或都给都会返回 422，而指定了相册的 `filters` 会像该相册自身的 GET 一样做访问检查——相册不存在返回 `404`，在受访问控制的安装上访问他人的相册返回 `403`。响应为 `{success, count}`，其中 `count` 是实际写入的行数 |

### 下载

| 端点 | 说明 |
|----------|-------------|
| `GET /api/download/options` | 某张照片可用的下载类型（`path`，可选 `is_shared`） |
| `GET /api/download` | 下载一张照片（`path`、`type=original\|darktable\|raw`，可选 `profile`） |
| `GET /api/photo/social_crop` | `[Edition]` 按某个社交平台宽高比预设下载裁切后的全分辨率 JPEG（`path`、`preset`） |
| `GET /api/photo/social_crop/preview` | `[Edition]` 只返回某个预设的归一化裁切矩形 + 取景依据（`path`、`preset`）——不解码原图 |

**下载类型：**

- `original`——按原样提供文件（JPG/HEIF），或把 RAW 文件用 rawpy 转换为 JPEG。
- `darktable`——用指定的 darktable 配置转换配套的 RAW（需要 `profile` 参数）。若不存在配套 RAW，则回退到原图。
- `raw`——按原样提供配套的 RAW 文件（在被分享的相册中不可用）。

`/api/download/options` 端点会自动检测配套的 RAW 文件，并返回包括已配置的 darktable 配置在内的可用选项。查看器用它来填充逐张照片的下载菜单。

`type=original` 会用查看器所显示的同一套渲染来转换 RAW，因此包围曝光中的某一帧下载出来时既没有相机预览也没有曝光增益——参见 [CONFIGURATION.md](CONFIGURATION.md#包围曝光照片按未校正方式渲染)。`type=raw` 和 `type=darktable` 不受影响。

**基于显著性的社交平台裁切。**当 `viewer.features.show_social_export` 为 `true`（默认）且编辑模式已解锁时，照片详情的下载栏会增加一个**社交平台裁切**菜单，列出已配置的 `social_export.presets`（开箱即用的有方形 1:1、竖幅 4:5、故事动态 9:16）。选择一个预设即可下载按该宽高比裁切、并以检测到的主体为中心取景的全分辨率 JPEG——这是 Lightroom 导出预设做不到的事。裁切窗口是能放进图像内部的、符合目标宽高比的最大矩形，以主体为中心并在边缘处夹紧。主体框来自一条回退链：已保存的 BiRefNet 主体框（`photos.subject_bbox`，由显著性处理过程和 `--recompute-saliency` 写入）→ 检测到的各人脸框的并集 → 普通的居中裁切。`preview` 端点会返回本次裁切是由哪一种来源驱动的（`saliency` / `faces` / `center`），并显示在菜单的提示文字中。原图解码复用与下载路径相同的 RAW（rawpy）和 HEIC（pillow-heif）加载器，并在裁切前应用 EXIF 方向。

| `POST /api/cull/apply` | `[Edition]` 把保留照片复制、或把淘汰照片移动／移入回收站到某个文件夹（参见[选片后导出／清理](#选片后导出清理)）。请求体 `{paths?, filters?, exclude?, action, target_dir?, include_companions, include_sequence_siblings, dry_run}`——必须恰好是 `paths`（最多 10000）或一组照片库 `filters` 之一，两者都给返回 `422`，都不给返回 `400`；`exclude`（可选，最多 1000）会从所发送的目标中剔除指定路径——从 `paths` 中减去，或从 `filters` 范围中排除——因此它只能收窄目标，绝不会扩大，而且被排除的路径也绝不会作为同组照片被重新加回来（它同样不计入 `sequence_siblings`）；指定了相册的 `filters` 会像该相册自身的 GET 一样做访问检查——相册不存在返回 `404`，在受访问控制的安装上访问他人的相册返回 `403`；`filters` 会走与 `GET /api/photos` 相同的归一化流程（查看器默认值加上 `type` 预设展开），因此它始终与它所来源的照片库视图一致。匹配超过 10000 张照片的 `filters` 会以 `412` 拒绝并给出数量和上限，该计数在构建任何路径列表之前完成，绝不截断，并且对试运行与真实执行同样强制——预览不能被拿来完成执行本身被拒绝去做的无界工作；`action` 为 `copy_keeps \| trash_rejects \| move_rejects`；`include_companions`（默认 `false`）会加上每个文件的同名配套 RAW 和 `.xmp`；`include_sequence_siblings`（默认 `false`）会加上与匹配照片共享 `(sequence_kind, sequence_group_id)` 的所有其他帧，**前提是它自身的淘汰状态与本次操作相符**，因此绝不会因为某个同组照片被淘汰就毁掉一张被保留的帧；`dry_run` 默认为 `true`。响应在 `skipped` / `excluded_by_state` / `not_visible` 之外还会加上 `matched`（符合本次操作条件的路径）和 `sequence_siblings`（同组照片帧数，即使该开关关闭也会报告） |

| 密码不生效 | 检查 `viewer.password`（单用户），或核对密码哈希（多用户） |
| 用户看不到照片 | 检查其用户配置中的 `directories` 以及 `shared_directories` |
| 没有扫描按钮 | 需要 `superadmin` 角色以及 `viewer.features.show_scan_button: true` |
| 搜索没有结果 | 确认照片已有 `clip_embedding` 数据（请先运行评分） |
| VLM 点评不可用 | 需要 16gb/24gb VRAM 配置档以及 `viewer.features.show_vlm_critique: true` |
| 地图上没有照片 | 运行 `--extract-gps` 填充 GPS 列，并确认照片带有 EXIF GPS 数据 |
| 无法生成照片描述 | 基于 VLM 的照片描述需要 16gb/24gb VRAM 配置档 |
| 时间线为空 | 确认照片有 `date_taken` 值 |
| 端口 5000 被占用 | 运行 `python viewer.py --port 5001`（或设置 `PORT=5001`）。在 macOS 上，控制中心的 AirPlay 接收器默认占用 5000——请换一个端口，或在“系统设置 → 通用 → 隔空投送与接力”中关闭 AirPlay 接收器。 |
